### 2.1 关键原则

**BMI 是派生数据，不落库。** 由 `weightKg` + `profile.heightCm` 实时计算。

- ✅ 好处：改身高后历史 BMI 自动一致
- ⚠️ 代价：若将来要「当时的 BMI」，需要引入身高快照字段

**Domain 层不依赖 Android。** 所有算法（BMI、分级、聚合、刻度、平滑）都是纯函数，可直接用 JVM 单测，不需要 Robolectric。

**取值规则集中在 `Aggregator` 一处。** UI 层不做任何聚合判断。

## 3. 数据模型

```kotlin
// 每次称重一条
@Entity(tableName = "weight_records", indices = [Index("measuredAt")])
data class WeightRecordEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val measuredAt: Long,          // epoch millis，带时分，支持一天多条
    val weightKg: Double,
    val bodyFatPercent: Double?,   // 可空
    val note: String?,             // 可空
    val createdAt: Long,
    val updatedAt: Long,
)

// 单行档案（DataStore，不是 Room 表）
data class UserProfile(
    val heightCm: Double? = null,
    val targetWeightKg: Double? = null,
    val targetSetAtWeightKg: Double? = null,   // 设置目标时的体重，用于进度条起点
    val bmiStandard: BmiStandard = BmiStandard.CHINA,
    val unitSystem: UnitSystem = UnitSystem.METRIC,
    val reminderEnabled: Boolean = false,
    val reminderTime: LocalTime? = null,
)
```

**索引**：`measuredAt` 必建 —— 图表的按时间范围查询、列表排序都靠它。

**BMI 不建表**。v1 数据量小，实时算即可；真需要性能优化再加缓存列，但那时要考虑身高变更的失效逻辑。

### 3.1 领域模型

```kotlin
enum class Metric { WEIGHT, BMI, BODY_FAT }      // 身高不进图表，故不在枚举内

data class BmiLevel(
    val level: Level,        // UNDERWEIGHT / NORMAL / OVERWEIGHT / OBESE
    val sliderPos: Float,    // 0f..1f，四色条上的归一化位置
    val standard: BmiStandard,
)

data class ChartPoint(
    val time: Long,          // 该点的代表时间（当日最低那条的时间戳）
    val value: Double,       // 按当前 Metric 取的值
    val sourceRecordId: Long // 关联的真实记录，点击气泡与命中测试用

```

> `ChartPoint` 带 `sourceRecordId` 很重要：切换指标时「当日最低值」必须锁定**同一条记录**，而不是三个指标各自取最小值。

## 4. 核心算法

### 4.1 BMI 计算与分级

```
bmi = weightKg / (heightCm / 100)^2      保留 1 位小数
```

分级用**中国标准**（决策 Q1）：

| 等级 | 区间 | 文案 |
|---|---|---|
| UNDERWEIGHT | < 18.5 | 较轻 |
| NORMAL | 18.5 – 23.9 | 标准 |
| OVERWEIGHT | 24.0 – 27.9 | 超重 |
| OBESE | ≥ 28.0 | 肥胖 |

返回完整的 `BmiLevel` 对象，UI 只负责渲染，**不重复判断逻辑**。

> **实现修正（M0 落地时发现）**：`BmiLevel` 原本还带 `label` / `rangeLabel` / `color`，实现时去掉了：
> 1. 那些是**本地化与主题**相关的 UI 关注点，放进 domain 会让 i18n 无从下手（决策 C5 要求字符串走 `strings.xml`）
> 2. `color` 是 Compose 类型，引入它会让 domain 层依赖 Android，破坏「domain 可纯 JVM 单测」这条约束
>
> UI 层用 `level` + `standard` 去 `strings.xml` 查文案、去 theme 查颜色即可。

### 4.2 四色条位置映射（四段等宽）

四段各占 25%，与 BMI 数值跨度无关。**因此滑块不能按 BMI 线性映射**：

```kotlin
val bounds = listOf(15.0 to 18.5, 18.5 to 24.0, 24.0 to 28.0, 28.0 to 35.0)
val i = bounds.indexOfFirst { bmi >= it.first && bmi < it.second }
    .let { if (it >= 0) it else if (bmi < 15.0) 0 else 3 }        // 越界贴边
val (a, b) = bounds[i]
val pos = (i + (bmi - a) / (b - a)) / 4.0                          // 0f..1f
```

- BMI < 15 → `pos = 0f`；BMI ≥ 35 → `pos = 1f`
- 边界值 `24.0` 归入**浅红段的起点**，与「24.0 起算超重」的分级文案一致

> 校验：BMI 22.4 → 第 2 段（绿，index 1），段内 `(22.4−18.5)/(24−18.5)=0.709`，`pos=(1+0.709)/4=0.427`

### 4.3 时间范围与聚合

| Tab | 范围 | 数据点粒度 | X 轴 5 个标签 |
|---|---|---|---|
| 日 | 当天 | 当天**全部原始记录**（按时间） | 时间点，如 `08:20` |
| 周 | **本周**（周一–周日） | 每天一个点（当日**最低值**） | 一 / 二 / … / 日，7 个 |
| 月 | **本月**（1 日–月末） | 每天一个点（当日**最低值**） | 1 / 10 / 20 / 月末 |
| 年 | **本年**（1/1–12/31） | 每月**平均值** | 1 至 12，12 个 |
| 总 | 首条记录 → 今天 | 天数 > 120 则按月聚合，否则按天（日均取**最低值**） | 起止 + 中间三等分 |

**⚠️ 实现要点：当日最低值必须锁定同一条记录。**

先按体重选出当日最低的那条，再取它的 BMI 和体脂率；**不能对三个指标各自独立取最小值**。否则同一天在图上会出现「最低体重」和「最低体脂」来自两次不同称重的错位。

```kotlin
// ✅ 正确：先选记录，再取值
val minRecord = dayRecords.minBy { it.weightKg }
ChartPoint(time = minRecord.measuredAt, value = metric.valueOf(minRecord), ...)

// ❌ 错误：指标各自取最小
val value = dayRecords.minOf { metric.valueOf(it) }
```

### 4.4 Y 轴刻度算法（4 主 + 次刻度）

> **硬性要求：四条主刻度的数字必须是整数。** 见 [02 设计规范 §2.4](02-设计规范.md)。
> 所以主步长**只从整数里选**，最小为 1 —— 刻度窗口因此至少 3 个单位宽。

```
1. 取数据 min/max。目标体重是否纳入见下方「目标线撑开限制」
2. 若 max == min（只有一条记录或全部相同）→ 上下各扩 1
3. 数据上下各留 8% 边距 → 得到 lo / hi
     ↑ 顺序不能反。先留边距再选步长，68.0–69.0 才会得到留了边距的 67/68/69/70，
       而不是紧贴的 68/69/70/71
4. 候选步长 = {1, 2, 3, 4, 5, 6, 8, 10} × 10^k（k = 0..2），升序，全是整数
5. 取第一个同时满足下面两条的候选 M：
     (a) lower + 3M ≥ hi，其中 lower = floor(lo / M) × M   ← 必须真的覆盖住数据
     (b) 存在次分段数 s 使 m = M / s 是「干净」的数
6. [lower, upper] = [snapCentered(center, M) , lower + 3M]
     snapCentered 把「让数据居中」的理想下界 center − 1.5M 四舍五入到最近的 M 的整数倍。
     原先写的是 floor(lo / M) × M —— 只会往下掉、从不往上抬，数据永远贴在窗口下半部分
7. 选次分段数 s（候选 4 / 3 / 5 / 2），默认 s = 4 → 两条主刻度之间插 3 条，共 13 条
   干净的标准：m 最多一位小数
8. 次刻度取值 = lower + i·m（跳过与主刻度重合的位置）
```

> **实现修正（M3 落地时发现的三个坑）**
>
> 1. **判据必须是 `lower + 3M ≥ hi`，不能是 `3M ≥ 跨度`。**
>    下界向下取整会掉到 `lo` 以下、吃掉 `3M` 的预算，用后者会让上界**低于数据最大值**，
>    折线顶部被裁到图外。这是渲染时肉眼发现的。
> 2. **步长挑选还要看「能否整除出干净的次步长」。**
>    只看覆盖的话，跨度 0.4 时会选中 0.15，而 0.15 无论怎么分段都得到两位小数
>    （0.15 / 2 = 0.075），刻度数字很难看。
> 3. **步长必须是整数。** 早先为了照顾小跨度，候选里放了 0.5 / 1.5 / 2.5，结果
>    一周体重只在 68.0–68.8 之间时，步长落到 0.4，刻度显示成 68.4 / 68.8 ——
>    与「取整数」的要求冲突。
>
> 已知代价：数据跨度很小时（比如一周只在 68.0–68.2 之间变动），整数刻度会让折线
> 只有约 7% 的高度、几乎是条平线。**这是刻意接受的**，后续如果实际用起来觉得太糟再议。

主步长 / 次步长对照：

| 数据范围 | 主步长 M | 4 个主刻度值 | s | 次步长 m | 总刻度线 |
|---|---|---|---|---|---|
| 68.0 – 69.0 | 1 | 67 / 68 / 69 / 70 | 5 | 0.2 | 16 |
| 68.0 – 69.5 | 1 | 67 / 68 / 69 / 70 | 5 | 0.2 | 16 |
| 66 – 72 | 4 | 64 / 68 / 72 / 76 | 4 | 1 | 13 |
| 66 – 75 | 4 | 64 / 68 / 72 / 76 | 4 | 1 | 13 |
| 64 – 76 | 6 | 60 / 66 / 72 / 78 | 4 | 1.5 | 13 |
| 65 – 80 | 10 | 60 / 70 / 80 / 90 | 4 | 2.5 | 13 |
| 20 – 200 | 80 | 0 / 80 / 160 / 240 | 4 | 20 | 13 |

**目标线超出范围的处理**：目标与数据区间的差值超过区间 30% 时，**不撑开 Y 轴**，改为在图表边缘显示方向箭头（决策 B8）。

### 4.5 X 轴标签

**刻度线不渲染**，但刻度位仍要计算，因为标签定位和点击命中测试依赖它。

- 刻度位**按「日历单位」铺满**（周 / 月 = 天，年 = 月），缺失日期**保留刻度位**。若只在有记录的日期算刻度，没称重的日子会出现空档，标签位置随之漂移
- 日历单位 > 40 个时按 2 / 3 / 5 抽稀
- **标签按视图分类**，不是统一的「5 个等分」——一周就是七个星期几、一年就是十二个月，这是日历直觉

```
6/1 – 6/30，四等分得到 1、8.25、15.5、22.75、30
→ 显示 6月1日、6月8日、6月16日、6月23日、6月30日
→ 位置分别是 0、0.25、0.5、0.75、1.0 的绘图区宽度
```

- ⚠️ **不能按数据点序号等分**（`days[round(i*(n-1)/4)]`）：遇到有缺口的月份，标签位置会随数据点漂移，间距忽宽忽窄，看起来像排版事故
- ⚠️ **也不能把标签吸附到最近的数据点**：吸附会造成 1–2 天的位置偏移，5 个标签的间距就不等了

### 4.6 折线平滑（monotone cubic）

选用 **Fritsch–Carlson 单调三次插值**，而不是 Catmull-Rom 或自然三次样条：

| 特性 | monotone cubic | 普通三次样条 / Catmull-Rom |
|---|---|---|
| 通过所有数据点 | ✅ | ✅ |
| 过冲 | **不会**，曲线始终落在相邻两点的值域内 | 会，可能画出低于最小值或高于最大值的**假峰假谷** |
| 保单调 | ✅ 上升段内不会冒出假的下降 | ❌ |
| 体重场景 | 安全 | 危险 |

**整条序列连续平滑，空缺处同样用实线**（决策 B17）。因此实现上**不需要**按日期连续性切段。

**实现要点**

- 平滑只影响**绘制**，不改变数据坐标；点击命中测试仍以真实点为准
- Hermite → Bezier 后用 `Path.cubicTo` 绘制（比逐点 `lineTo` 采样更快也更平滑）：
  `P1 = (x0 + dx/3, y0 + m0·dx/3)`，`P2 = (x1 − dx/3, y1 − m1·dx/3)`
- 退化情况：1 个点 → 画单点；2 个点 → 直接直线（切线无法定义）
- 平滑后**空心圆点是唯一的「真实测量」标记**，曲线本身不代表已测量的值

## 6. 图表实现方案

| 方案 | 优点 | 缺点 | 适配度 |
|---|---|---|---|
| **自绘 Canvas** ✅ | 100% 贴合设计；零依赖；体积小 | 刻度算法、手势、性能要自己写，约 300–500 行 | ★★★★★ |
| Vico | Compose 原生，API 现代，支持渐变 / 虚线 | 自动刻度策略与「恰好 4 档整数」会打架，需大量 override | ★★★☆☆ |
| YCharts | Compose 原生，较活跃 | 同上，且 API 稳定性一般 | ★★★☆☆ |
| MPAndroidChart | 功能最全 | View 体系，与 Compose 交互别扭，上游已停更 | ★★☆☆☆ |

**结论：自绘。** 这个设计本质上是在「画」而不是「配置」——4 档整数刻度、5 个 X 标签、空心圆点、渐变填充、虚线目标线带左侧标签。用图表库反而要一路对抗它的默认行为。而且「四色条 + 三角滑块」无论如何都得自绘，索性统一。

### 6.1 绘制层级（自下而上）

```
1. 次刻度线（9 条，#F2F2F2）
2. 主刻度线（4 条，#F0F0F0）
3. 渐变填充（折线下方，#3DD68C 20% → 0%）
4. 目标虚线（#3DD68C 1.5dp，带左侧标签）
5. 折线（monotone cubic，#3DD68C 2dp）
6. 空心数据点（半径 4dp，描边 2dp）
7. X 轴日期文字（按视图分类，无刻度线）
8. 点击气泡（最上层）
```

### 6.2 点击命中测试

- 以真实数据点的**像素坐标**为基准，命中半径取 `max(24dp, 相邻点间距/2)`
- 平滑曲线上的插值点**不参与命中**
- 命中后弹出气泡：日期 + 数值 + 与上一点的变化量

## 7. 风险与坑

| # | 风险 | 说明与对策 |
|---|---|---|
| **R2** | **依赖下载受网络环境影响** | Gradle 首次构建要从 `services.gradle.org` 与 Maven 仓库拉依赖，在国内网络下**可能超时**。解法是在 `~/.gradle/gradle.properties` 写 `systemProp.https.proxyHost/Port`，或改用国内镜像源（代价：代理/镜像不可用时构建会失败，且镜像的制品可能滞后） |
| **R3** | **Navigation3 较新** | 模板自带，但需确认生产可用性与文档成熟度；必要时换回 Navigation Compose |
| **R4** | **AGP 9 / JDK 25 组合较激进** | 当前实测通过（Gradle 9.1.0 明确支持 Java 25），但第三方库（Hilt / KSP）可能有兼容缺口，引入前先验证 |
| **R5** | **手势冲突** | ~~三层嵌套~~ **已消解**：图表区不再消费横向手势，只剩「页面纵向滚动 ↔ 概览卡片横向滚动」两层 |
| **R6** | **数字动画抖动** | 大号体重数字做动画时，非等宽数字会导致宽度跳动。需用 `FontFeatureSetting("tnum")` |
| **R7** | **纯白背景上卡片阴影不可见** | 用 `#FAFAFA` 填充 + `#F0F0F0` 发丝描边替代 elevation |
| **R8** | **一天多条的 X 轴退化** | 已由「当日最低值」规则解决，但实现时必须锁定同一条记录，见 §4.3 |
| **R9** | **空数据 / 单点 / 全等值** | 三种退化场景都必须能正确渲染，不能崩也不能空白。骨架屏与空状态见 [设计规范 §6](02-设计规范.md) |
| **R10** | **视口滚动在「日 / 周」视图无效果** | ~~风险~~ **已消解**：视口滚动整个功能已移除，五个视图都一次画完整段范围 |

> R1（`java.time` 需要 desugaring）**已消除**：最低版本确认为 minSdk 26，`java.time` 原生可用。

这些问题在设计与验证阶段出现过，记录以免重蹈：

| 问题 | 现象 | 结论 |
|---|---|---|
| 次刻度色不可见 | `#F7F7F7` 在纯白背景上几乎看不见，7 条和 13 条刻度渲染出来没差别 | 改 `#F2F2F2` |
| X 轴标签间距不均 | 按数据点序号等分，遇到缺数据的月份标签忽宽忽窄 | 改为按位置四等分，不吸附数据点 |
| X 轴刻度线太碎 | 月视图 30 条日历刻度，图面很乱 | 刻度线全部不渲染，只留 5 个日期文字 |
| 平滑插值误导 | 跨空缺的平滑曲线看起来像真的连续测量过 | 曾用虚线区分，因破坏观感而放弃；改由空心点承担「实测」语义 |
| 等宽色条滑块错位 | 四段等宽后仍按 BMI 线性映射，滑块与色块对不上 | 改为「段索引 + 段内比例」映射 |
