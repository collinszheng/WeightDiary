## 3. 数据模型

### 3.1 新增两列 + 一张墓碑表

| 列 | 类型 | 默认 | 用途 |
|---|---|---|---|
| `source` | `TEXT NOT NULL` | `'MANUAL'` | 来源枚举名，沿用 `BmiStandard` / `UnitSystem` 存 `.name` 的既有做法 |
| `externalId` | `TEXT NULL` | `NULL` | Health Connect 的 `metadata.id`，用于去重 |

**唯一索引 `externalId`**。SQLite 的唯一索引把多个 `NULL` 视为互不相同，所以手动记录（`externalId` 为 `NULL`）可以有很多条 —— 这一点是整个去重设计的基石，不是巧合。

新表 `ignored_external_ids`：用户删掉一条同步记录后，把它的 `externalId` 记进去，下次同步跳过（06 §7.3 的「已忽略的外部 id」方案）。少了它，删掉的记录下次同步就会复活。

### 3.2 Migration 1 → 2

```sql
ALTER TABLE weight_records ADD COLUMN source TEXT NOT NULL DEFAULT 'MANUAL';
ALTER TABLE weight_records ADD COLUMN externalId TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS index_weight_records_externalId ON weight_records (externalId);
CREATE TABLE IF NOT EXISTS ignored_external_ids (...);
```

两条纪律：

- **绝不重建表**（06 §7.2）。重建会丢数据，而本项目刻意不提供 `fallbackToDestructiveMigration` —— 写错就是老用户数据全丢。
- **迁移里的 DDL 必须与 Room 生成的逐字一致**，否则开机 `validateMigration` 直接抛 `Migration didn't properly handle`。做法：先把 entity 写好编译一次，照 `app/schemas/com.weightdiary.app.data.local.WeightDatabase/2.json` 里的 `createSql` 抄，**不要手写**。

### 3.3 domain 模型只加 `source`

`domain/model/WeightRecord` 加 `source`，**不加 `externalId`**：

- `source` 是记录的固有属性（UI 要显示来源、CSV 语义要用）
- `externalId` 是持久层的去重键，domain 不需要知道 —— 免得污染 `RecordRows` / `ChartPoint`

`SyncPlanner` 通过一个专门的入参类型拿 `externalId`，不把实体类型引进 domain（domain 层不依赖 Android 的约定，见 AGENTS 架构约定）。

## 4. 去重与过滤

### 4.1 三层去重

| 层 | 机制 | 防的是 |
|---|---|---|
| 1 | `externalId` 唯一索引 | 重复拉取、重叠窗口、点了两次同步 |
| 2 | **配对**：HC 的体重与体脂率是**两条独立记录**（各有自己的 `metadata.id`），按「同一本地日 + 时间最近」配成一次称重 | 配错导致体脂率挂到别人的体重上 |
| 3 | **邻近认领**（方案 B）：库里已有「同一本地日 且 体重差 ≤0.1kg」的记录时，**不插新行，把 `externalId` 写到那条记录上** | 手动记过一条 + HC 又读回来一条 |

### 4.2 判据用「同一天 + 体重」而不是「±5 分钟」

**手动记录的时分不可信**：`AddRecordForm` 的时间默认取打开表单那一刻，而时间选择器是死代码（见 §10 待办）。早上 07:48 称的、晚上 22:00 才记，存进去就是 22:00。

所以「±5 分钟」这种按时间戳配对的逻辑在本 App 里**几乎永远不会命中**。可用的信号只有两个：

- **日期** —— 用户能选，基本准确
- **体重** —— 手敲的，1 位小数

判据因此定为：**同一本地日（按 `ZoneId.systemDefault()`，跨零点沿用决策 B12「凌晨算当天」的口径）且 `|Δ体重| ≤ 0.1kg`**。0.1kg 的容差正好覆盖手动只让填 1 位小数的舍入误差（最大 0.05kg）。

### 4.3 时间边界（一刀切）

```
T = 库里 source = MANUAL 的记录中最大的 measuredAt
丢弃所有 measuredAt ≤ T 的 HC 记录
```

**库里没有手动记录时不设边界。** 这是为什么首次接入必须先是「先引导用户手动记一条自己的体重」（§6）—— 那条引导记录同时提供边界和异常过滤的锚点。**跳过引导就等于无过滤地吞下 30 天混合数据**，所以引导是强制前置步骤，不是可选优化。

### 4.4 异常过滤（宁可漏，不可错）

共用体脂秤（一家人）是真实场景，而 **Health Connect 里没有「人」这个维度**：`metadata.dataOrigin` 是写入的 App、`metadata.device` 是秤，都不识别人。所以做不到「识别出这是谁」，只能做**「这条与你自己历史是否一致」**。

```
接受条件：|w − anchor| ≤ max(3.0 kg, 5% × anchor)
```

- **锚点是滚动的**：按时间顺序 fold，每接受一条就把锚点推过去。这样正常缓慢减重（78 → 75 花三个月）不会被误杀，而一次 55kg 会被挡住。所以它是 fold，不是一次性比较（有专门的守门单测：四步各 2.0kg、累计 8.0kg，一次性比较会误杀最后一条）。
- **锚点取库里最新的那条体重（含同步来的）**，不优先取手动记录 —— 三个月前的手动记录会把锚点钉在旧体重上，反而把现在合法的体重判成异常。而「锚点被脏数据污染」这个担心不成立：脏数据本来就被这道过滤挡在门外。
- **库里一条记录都没有时不设锚点，也就是不过滤** —— 没有基准就没有判断依据。这正是首次接入必须先手动记一条的原因（§4.3）。
- **被拒的记录不入库、也不记墓碑** → 每次同步重新判一次。用户体重真的变了（产后、生病）时这些记录会自己「解禁」，不需要人工干预。

取舍是**宁可漏不可错**：漏掉的记录用户能手动补、能看出来；错的记录会静默毁掉整张趋势图 —— 周/月视图按「当日最低值」取值（决策 B15），一条 55kg 混在 78kg 区间里会把折线压扁；若它恰好是最新一条，首页变化量会被算成 `↓ 22.8kg`。而这个 App 的全部价值就是那条趋势线。

> **3.0kg / 5% 是要靠真实数据校准的常量**，集中在一处并注明取舍来源，别散成魔法数字。

### 4.5 范围过滤

复用既有的 `RecordValidator`（**不改它**）：

- `validateWeight` / `validateBodyFat` 不通过 → 丢弃并计数
- `measuredAt > now + 10 分钟` → 丢弃并计数（设备时钟偏移；**不复用** `validateMeasuredAt` 那个 +60 秒的输入容差，它服务的是「选了当前时刻却报未来」的假失败，语义不同）

注意这是对决策 B10 的一次**语境收窄**，不是推翻：B10「超出范围直接拒绝」的理由是**挡手滑**（68.5 输成 685），而拉取的数据没有手滑，也没有「保存按钮」可以禁用。同步路径把「错误」映射成「跳过 + 计数」。

### 4.6 算法总览（`SyncPlanner`）

纯函数，无 Android 依赖，可直接 JVM 单测。

```
输入：existing（含 source/externalId）、tombstones、pulled（体重 + 体脂率原始记录）

1. 配对     → 称重事件（externalId = 体重记录的 metadata.id）
2. 边界     → 丢弃 measuredAt ≤ T
3. 墓碑     → 丢弃 externalId ∈ tombstones
4. 幂等     → 丢弃 externalId 已在 existing 中
5. 认领     → 同日同重则把 externalId 写到已有记录上，不插新行
6. 范围过滤 → 丢弃越界 / 未来时间
7. 异常过滤 → 丢弃 |w − anchor| 超阈值（不推进锚点）
8. 插入     → 按时间升序批量插入（OnConflictStrategy.IGNORE 兜底）
```

输出 `SyncPlan(inserts, claims, skipped: Map<SkipReason, Int>)`，`SkipReason` 至少含 `BOUNDARY / TOMBSTONE / DUPLICATE / OUT_OF_RANGE / OUTLIER / UNPAIRED_BODY_FAT`，用于「跳过 N 条」的报数。

## 5. 同步时机与窗口

| 项 | 结论 | 为什么 |
|---|---|---|
| 触发 | **打开 App 前台拉一次 + 设置页手动「立即同步」** | Health Connect 的后台读取要用户另外去系统里开「在后台访问数据」（06 §3 已核实），路径很深；为一个体重记录引入 WorkManager 依赖 + 一个用户大概率不会开的开关，不划算 |
| 窗口 | **只拉最近 30 天** | 30 天是官方契约（06 §3） |
| `READ_HEALTH_DATA_HISTORY` | **不申请** | 要走 Play 审批，对体重 App 不划算 |
| 增量 | `max(30 天, 上次同步时间 − 7 天重叠)`，`lastSyncAt` 存 DataStore | 重叠是为了兜「品牌 App 延迟写入」（称完三天后才同步进 HC） |

> ⚠️ **30 天窗口实际上是摆设。** §4.3 的边界（最后一条手动记录）在首次接入后永远比 30 天更严，所以真正限制范围的一直是边界。这里保留 30 天只是因为它同时也是 HC 的硬限制，写清楚免得后人以为是死代码。

## 6. UI

### 6.1 入口

**独立成设置页的「实验功能」一节**（2026-10 改的，推翻了原先「并入数据管理、成为第 4 行」的决定 —— 理由见 [`04` §7.6](04-决策记录.md)）。不再和数据进出同组，是因为它能不能用**取决于第三方 App 愿不愿意往 HC 写**（小米官方那个 App 就不写），放在「数据管理」里会让人误以为这是本 App 自带的能力。

沿用现成的私有组件：`SettingsRow` / `SectionLabel` / `SettingsGroup` / `GroupDivider`。

**API < 28 时整节连同标题一起不出现** —— 宁可功能不出现，也不能留一张空卡片配一句「此功能不支持」。

### 6.2 首次接入引导（强制）

**先让用户手动记一条自己的体重，再接入。** 复用已有的「添加数据」流程，零新界面。

这条引导同时解决两件事：

1. §4.4 异常过滤的**锚点** —— 没有基准时，第一次同步会把一家人的数据无差别吞进来
2. §4.3 时间边界的 `T`

### 6.3 状态与文案

| 状态 | 表现 |
|---|---|
| API < 28 | **整行不显示**（06 §2.2；设计规范也有「宁可功能不出现，也不能画错位置」的先例） |
| HC 未安装（API 28–33） | 显示行，描述改为「需要安装健康数据共享」 |
| 未授权 | 显示行，点击走权限申请 |
| 已授权 | 显示「上次同步时间 / 已同步 N 条」+ 「立即同步」 |

### 6.4 首次同步必然 0 条 —— 文案必须处理好

引导记录的时间 ≈ 现在，所以边界 `T` ≈ 现在，**30 天内所有 HC 记录都被一刀切丢掉**。首次同步的结果就是 0 条。

这是**有意为之**（产品决定：不要历史，从现在开始同步），但**不能只报「0 条」**，否则用户会以为坏了。要有一条明确文案，例如「已连接，将从现在开始记录新的称重」。

## 7. 权限与清单

要加的是 health 类读取权限 + `<queries>`（API 30+ 才看得见 HC 是否安装）+ Android 14 要求的权限说明 Activity 别名。**具体字符串必须逐字核对官方文档后再写**，不靠记忆 —— 这类东西写错是静默失效。

**唯一的破口是合并后的清单**：依赖的清单会合并进来，`INTERNET` 只可能从那里漏进来。所以约束用**脚本对合并清单做断言**（§9），而不是靠肉眼看源码清单。

连带文案：设置页「关于」和 `README.md` 的表述从「零权限」改成 **「没有网络权限」** —— 卖点没变，但表述要和清单事实一致。

## 8. 分层与落点

| 位置 | 内容 | 依据 |
|---|---|---|
| `domain/sync/` | `SyncModels` / `MeasurementPairing` / `SyncPlanner` —— 配对、边界、判重、过滤，纯 Kotlin | 照 `domain/record/RecordCsv` 的先例 |
| `data/healthconnect/` | `HealthConnectSource`：可用性、权限、30 天分页读取 | 照 `data/backup/RecordBackup` 的先例（碰 SDK 的适配器放 data） |
| `data/sync/` | `WeightSyncCoordinator`：编排「读 → 配对 → 规划 → 落库」，`SyncOutcome` 给 UI | 判断逻辑一条都不在这里 |
| `data/prefs/SyncStore.kt` | `lastSyncAt` 水位线 | 独立于 `ProfileStore`（那是用户档案） |
| `data/repository/WeightRepository` | 唯一写入口；`delete` 写墓碑、`clearAll` 连墓碑与水位线一起清、`applySyncPlan` 一个事务 | UI 层只跟仓库打交道 |
| `di/AppContainer` | 手写注入 | **不加 Hilt**（`04` 被否方案） |

执行顺序（刻意先便宜后贵，且边界是硬的）：

```
① 时间边界（一刀切）  →  ② 墓碑  →  ③ 幂等  →  ④ 时间/范围合法性
                      →  ⑤ 邻近认领  →  ⑥ 异常过滤（锚点 fold）
```

CSV 导出/导入的 4 列表头**本期不动**，`RecordCsvTest` 的 14 个用例保持原样：那份文件是给人用 Excel 看的，`externalId` 导出无意义。代价见 §10 第 6 条。

## 9. 验证

### 9.1 迁移（最重要）

**常规方法测不出迁移错误。** 按 06 §7.4：

1. 装 `dist/WeightDiary-1.0.apk`（与新版**同一签名**）
2. 记几条数据，**包括体脂**
3. **直接覆盖安装新版** —— 不要卸载、不要 `pm clear`
4. 确认：数据还在、体脂还在、图表正常、能新增

**第 3 步不能卸载**：卸载重装走的是「全新建表」路径，**根本不会触发 Migration**。这是 AGENTS 红线 #4「写入并读回」的跨版本版本。

### 9.2 硬约束

`tools/verify-no-internet.ps1` **解析合并后清单里的 `<uses-permission>` 元素**，断言没有
`INTERNET`。`debug` / `release` 两个变体都要跑。

两个坑都踩过，写进脚本了：

- **不能只在整份文件里搜「INTERNET」** —— 清单的注释里就有这个词（用来说明为什么没有它），
  子串匹配会直接误报。必须解析权限元素。
- 注意 AGENTS 红线 #1：`tools/*.ps1` 必须带 UTF-8 BOM，改完立刻做语法检查。
- 本机执行策略禁止运行未签名脚本，用 `-ExecutionPolicy Bypass`（环境属性，不是脚本问题）。

### 9.3 单测

- 现有 130 个必须全绿；本次共 **+33 个**（合计 163）
  后来真机测试又为两个 bug 各补了回归用例（[09 §6.6](09-真机实测记录.md) 的目标线、
  §6.15 的体脂配对），最终是 **166 个**
- `SyncPlanner`（19 个）：三层去重、时间边界、墓碑、邻近认领、范围与未来时间、
  异常过滤的**滚动锚点**（含「四步各 2kg、累计 8kg 不被误杀」的守门用例）
- `MeasurementPairing`（6 个）：同日最近优先、一条体脂只能用一次、跨天不配
- `HealthConnectAvailability`（7 个）：**API 28 门槛的 26 / 27 / 28 边界**，
  以及「版本不够时忽略 SDK 状态」。门槛被抽成纯函数就是为了能这样钉死 ——
  手边的模拟器是 API 37，覆盖不到 8.0 / 8.1
- 照现有约定：JUnit4、固定 `ZoneId.of("Asia/Shanghai")`、中文反引号命名且说明**为什么**

> 反引号名字里**不能用 `>`**（JVM 方法名非法字符），用 `→` 代替。

### 9.4 其它

- **红线 #4**：若为 HC 库动了 proguard 规则，`assembleRelease` 后**实跑「写一条读回」**（编译期发现不了）
- **真机降级路径**：API 28 门槛（8.0/8.1 不显示入口）、HC 未安装、拒绝授权 —— 06 §8 的实测项一条都没做

（*"data from the past 30 days"*），给 `06` §3 那条官方契约又添了一个独立佐证。

`app/src/androidTest/java/com/weightdiary/app/data/local/WeightDatabaseMigrationTest.kt`，
跑 `./gradlew connectedDebugAndroidTest`。

在这之前，v1 → v2 只能手工覆盖安装验（`06` §7.4）—— 那种方法**测不出「哪些数据丢了」**，
只能看出「应用崩没崩」，而且每加一版迁移都要重跑一遍。现在这个测试：

1. 用 **v1 的 DDL**（逐字抄自 `app/schemas/.../1.json` 的 `createSql`）裸建一个真正的 v1 库
2. 塞两条老记录，**一条带体脂、一条不带**（可空列最容易在迁移里出事）
3. **用生产同样的配置打开** —— Room 会跑 `MIGRATION_1_2`，再拿生成的 identity hash 校验结构，
   对不上就抛异常。所以「迁移写错了」由 Room 自己举报，**不需要手写结构断言**
4. 再用 DAO 验数据、验墓碑表，以及**唯一索引的两个承重行为**：
   `externalId` 撞了就插不进去、多个 `NULL` 可以共存

**为什么不用 `androidx.room:room-testing` 的 `MigrationTestHelper`**：它会把
`androidx.lifecycle:lifecycle-viewmodel-savedstate:2.10.0` 带的
`kotlinx-serialization-core:1.7.3` 与 `room-migration:2.8.5` 要的 `1.8.1` 撞在一起
（AGP 的 consistent resolution 把 app 侧的 1.7.3 作为 **strict** 约束复制进 androidTest 的
classpath），运行时直接 `AbstractMethodError`。要修就得为一个测试去抬**生产**的依赖版本 ——
而上面这条路验的是同一条真实路径，且零新增生产依赖。

## 10. 已知限制

1. **边界之前、用户确实没记过的 HC 数据永远进不来**（§4.3 一刀切的代价）
2. **首次同步必然 0 条**（§6.4）
3. **30 天窗口与 `READ_HEALTH_DATA_HISTORY` 实际用不上**（§5）
4. **两个人体重接近时无法区分**（妈妈 55.2 / 女儿 54.8）。HC 里没有任何信息能区分她们，这是信息量不足，不是阈值没调好
5. **同步先进库、用户后手动记了同一次称重** → 两条并存。图表按当日最低值取值不受影响，但历史列表会多一行；若它是最新一条，首页变化量可能被压成 `0.0`。本期不处理
6. **CSV 导出丢失 `externalId`** → 换机导入后边界之前的记录可能重复（§4.1 第 3 层的邻近认领能兜住一部分）
7. **手动录入的时分不可选**（见下面的待办）
8. **HC 未安装 / 未授权 / API < 28 的降级路径未实测**（06 §8）
9. **多成员档案本期不做** —— 那是家庭共用的真正解法（切换用户、各自的目标与 BMI 标准），要动 `UserProfile` / 目标体重 / BMI 标准 / 图表 / 设置页，是另一个 feature 的量级。`04` 的被否方案里没有这一条，属于「没考虑过」而非「已否掉」，已登记为立项候选
10. **方案 B（§4.1 第 3 层）实际覆盖的面很窄**：一刀切之下 `T` 是所有手动记录时间的最大值，任何 `> T` 的记录都在全部手动记录之后，因此「HC 记录与手动记录同日同重」只可能发生在 `T` 当天的更晚时刻。保留它是因为成本极低（一个纯函数 + 几个单测），且将来若把边界改回「逐条核对」它立刻变成主力
11. **~~权限说明 Activity 没有写进清单~~ —— 已修，而且当初的判断是错的。** 起初以为它只影响上架合规，实际它是**功能性的**：HC 的授权页在弹出前会解析 `ACTION_SHOW_PERMISSIONS_RATIONALE`，解析不到就 `finish()`（HC 自己的日志：`E PermissionsActivity: App should support rationale intent, finishing!`），用户看到的是「点那一行什么也没发生」。已补上 `PermissionsRationaleActivity` + `activity-alias`，四个字面量全部从实机提取核实。经过见 [`04-决策记录` §7.4](04-决策记录.md)。<br>（对照：`READ_WEIGHT` / `READ_BODY_FAT` 两条也是**核实过**的 —— 直接从 1.1.0 的 AAR 里提取。）
