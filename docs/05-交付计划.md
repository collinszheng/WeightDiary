> Y 轴上界低于数据最大值导致折线被裁、极小跨度选出两位小数次步长、刻度非整数、
> 以及**内容比视口窄时可视窗口被放大**（周视图 X 轴标签跑到 10 月、曲线挤在左边一小块，
> 点击也因此全部落空）。

> **本阶段是项目最大的风险点**，建议按下面的顺序做，每步都能单独验证。

### 建议实现顺序

| 步 | 内容 | 可验证的产出 |
|---|---|---|
| 1 | `RangeResolver`：Tab + 基准日期 → (start, end, granularity) | 单测：5 个 Tab × 边界日期 |
| 2 | `Aggregator`：按粒度聚合，**当日最低值锁定同一条记录** | 单测：一天多条时三个指标来自同一记录 |
| 3 | `ChartScaffolder`：Y 轴 13 条刻度、X 轴刻度位与 5 个标签位置 | 单测：各种数据跨度下的主/次步长 |
| 4 | `MonotoneCubic`：Fritsch–Carlson + Hermite→Bezier | 单测：**不过冲**、保单调、1 点 / 2 点退化 |
| 5 | 静态 Canvas：只画刻度线 + 折线 + 数据点 | 屏幕上能看到图 |
| 6 | 渐变填充 + 目标虚线 + 轴文字 | 与设计稿对照 |
| 7 | Tab 切换与日期范围箭头 | 交互闭环 |
| 8 | 视口滚动 + 手势方向判定 | 与页面纵向滚动不打架 |
| 9 | 点击命中测试 + 气泡 | 点数据点出详情 |

### 深色模式 —— 已勘察，未开工

2026-10 讨论后搁置。**架构上确实准备好了，但不是「加一套色值」就完事**，下面是勘察结论，
开工前先读这一节，别重新查一遍。

#### 已经就位的

- 所有应用自绘颜色都走 `WeightDiaryTheme.colors`，**全局只有 1 处硬编码**：
  `WeightChart` 里数据点的内部填充 `drawCircle(Color.White, …)`
- 其余 7 处 `Color.White` 都压在强调色或红色的底上（FAB 加号、主按钮文字、左滑删除按钮），
  深色下不用改
- 状态栏图标**不用处理**：`MainActivity` 调的是无参 `enableEdgeToEdge()`，
  默认 `SystemBarStyle.auto`，会跟着系统深色模式自动切图标明暗

#### 三个坑

**① 启动白闪。** `res/values/themes.xml` 的 `android:windowBackground` 硬编码成
`@android:color/white`，父主题也是 `android:Theme.Material.Light`。深色下每次启动会闪一下白。
需要补 `values-night/themes.xml`，顺带处理 `forceDarkAllowed`。

**② 光有 `WeightDiaryColors` 不够，还要一套完整的 `darkColorScheme()`。**
`Theme.kt` 现在只定义了 `lightColorScheme()` 且只填了 11 个槽位，其余走浅色默认值。
而用了这些 Material3 组件，它们取的是 `MaterialTheme.colorScheme` 而不是我们的 token：

| 组件 | 用在哪 | 深色下不处理会怎样 |
|---|---|---|
| `ModalBottomSheet` ×4 | 添加数据 / 编辑资料 / 全部记录 / 引导页 | 还是白的 |
| `AlertDialog` | 设置页「清空所有数据」 | 还是白的 |
| `SnackbarHost` | 全局提示 / 删除撤销 | 底色 `inverseSurface` 不对 |
| `Scaffold` | 主框架 | |

**这是工作量的大头。** 另一个思路是给这几个组件显式指定自己的 token 颜色、绕开 Material 默认值 ——
代码少，但每个组件都要单独处理，容易漏。

**③ 两个语义反转的坑（第一个现在就是潜在 bug）。**

```kotlin
// WeightChart 的气泡
val tooltipStyle = typo.axis.copy(color = Color.White)   // 白字
...
background = colors.textPrimary,                          // 底色取「主文字色」
```

浅色下 `textPrimary` 是近黑，白字压上去没问题；深色下它会变成**近白** ——
**白底白字，气泡直接消失**。底色应该是一个独立 token，不该复用 `textPrimary`。
同一类问题还有上面提到的数据点白色填充。

#### 一个待定的设计问题

**BMI 四色条要不要为深色调亮？** 实测对比度：

| 色 | 白底 | 深色卡片 `#1C1C1E` 上 |
|---|---|---|
| 黄 `#FFCC00` | 1.5:1 | 11.7:1 |
| 绿 `#3DD68C` | 1.9:1 | 9.5:1 |
| 浅红 `#FF6B6B` | 2.9:1 | 6.3:1 |
| **深红 `#D0021B`** | 5.7:1 | **2.2:1 ← 会糊** |

建议调（iOS 自己就这么做：`systemRed` 浅 `#FF3B30` / 深 `#FF453A`），四色条是大面积色块不是细线。
代价是**同一个 BMI 等级在两种模式下是两种红**。

#### 开工时一并做的

- **对比度单测**：`textPrimary/background ≥ 4.5:1`、`textSecondary/cardFill ≥ 3:1`、
  `accent/cardFill ≥ 3:1`，浅深两套都跑。`Color.luminance()` 是纯 Kotlin，JVM 单测能直接跑。
  深红那个 2.2:1 就是靠算才发现的，肉眼看模拟器很容易漏
- 设置项：`UserProfile` 加 `themeMode`（**DataStore 无迁移成本**，给默认值即可）。
  形态待定：只跟随系统 / 跟随 + 手动覆盖（三档）/ 只有开关
- 设计规范 §2 的 token 表加一列深色值
- `docs/assets/render/` 四个脚本加 dark 参数，README 补深色截图

#### 还没定的三件事

1. 设置形态：只跟随系统 / 三档（跟随 + 浅色 + 深色）/ 只有开关
2. BMI 四色条的深红调不调
3. `darkColorScheme()` 老老实实补齐，还是绕开 Material 默认值
