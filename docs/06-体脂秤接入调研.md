# 06 · 体脂秤接入调研

> **状态**：调研完成，**已开工**。
> **核实日期**：2026-10-07。外部事实会变（尤其日期和品牌支持情况），超过半年请重新核实。
>
> ⚠️ **实现方案见 [`08-Health Connect 同步设计.md`](08-Health Connect 同步设计.md)。**
> 本文只回答「能不能接、为什么是 Health Connect」；「怎么接」（数据模型、去重、过滤、
> 权限、UI、验证）全在 08 —— 别在本文里找实现细节，也别重新调研一遍选型。

本文只回答「能不能接、怎么接、接了之后要动什么」。**具体设计见开工后另出的方案。**

---

## 1. 结论

**Android 端自动同步体脂秤数据，唯一不破坏本项目定位的方案是 Health Connect。**

| 方案 | 结论 |
|---|---|
| **Health Connect** | ✅ **首选**。纯本地 IPC，**不需要 `INTERNET` 权限**，与「不联网」定位兼容 |
| **BLE 直读** | ⚠️ 唯一完全离线、不依赖任何第三方 App 的方案，但成本最高、最脆。作为长期备选 |
| **小米云令牌** | ❌ 需要 `INTERNET` + 小米账号密码，**直接摧毁核心卖点**。不要做 |
| **MIoT** | ❌ 同上，且体成分属性开放不全 |

判断依据不是「哪个容易」，而是 **`AndroidManifest.xml` 里从来没有（也不会有）`INTERNET`**。
这是本项目最硬的卖点，任何需要联网的方案都要先过这一关。

> **2026-10 更正**：本文写作时清单是**零权限**；后来接入 HC 加了 2 条
>（`health.READ_WEIGHT` / `health.READ_BODY_FAT`），**`INTERNET` 仍然没有**。
> 「不联网」这个卖点没变，但「零权限」不再成立 —— 详见 §2.1。

> **iOS 不在范围内。** 本项目是纯 Android（Kotlin + Compose + Room），没有 iOS 版本。
> 搜集到的资料里大量提到 Apple Health / HealthKit，**全部不适用**，本文已剔除。

## 2. 对本项目的三条硬约束

### 2.1 不能新增 `INTERNET` 权限

`app/src/main/AndroidManifest.xml` **从来没有声明过 `INTERNET`**。
Health Connect 是设备内的进程间通信，读的是系统健康数据库，**不需要网络权限**。

**这条是选型的第一判据，比实现难度重要得多。**

> 措辞上要分清两件事：**「没有网络权限」成立，「零权限」不成立**。
> 接入 HC 之后清单里多了 2 条 health 读权限（见 [08](08-Health%20Connect%20同步设计.md)），
> 对外文案也相应从「零权限」改成了「没有网络权限」。

### 2.2 Health Connect 要求 API 28，而本项目 minSdk 是 26

官方原文：*"Health Connect requires a mobile device running Android 9 (API 28) or higher"*
（[availability](https://developer.android.com/health-and-fitness/health-connect/availability)，另有 [APKMirror 的 Android 9.0+ 标注](https://www.apkmirror.com/apk/google-inc/health-connect-by-android/variant-%7B%22arches_slug%22%3A%5B%5D%2C%22minapi_slug%22%3A%22minapi-28%22%7D/)佐证）

**minSdk 保持 26 不动**，但要加运行时版本判断：8.0 / 8.1 设备上不显示这个入口，
否则用户会看到一个永远可点、永远失败的按钮。

| Android 版本 | Health Connect |
|---|---|
| 14 (API 34) + | 系统内置 |
| 9–13 | 需用户从应用商店单独安装 |
| 8.0 / 8.1 | **不支持** |

### 2.3 表结构变更必须写 Migration

见 [AGENTS.md 红线 #5](../AGENTS.md)。本项目**刻意不提供 `fallbackToDestructiveMigration`**，
写错 Migration 就是老用户数据全丢。

## 4. 被推翻的说法

搜集到的资料里有两处错误，**都是会误导决策的那种**：

### ❌「Google Fit 第三方 API 已于 2025 年 6 月终止服务」

**官方现文是支持到 2026 年底**（[来源](https://developer.android.google.cn/health-and-fitness/health-connect/migration/fit?hl=en)）。

差别很大：按错的说法，依赖 Google Fit 中转的方案已经死了；按实际的，**它短期内还能用**。
（「2025 年 6 月」可能是旧公告后来延期了，以官方现文为准。）

### ⚠️「30 天限制是开发者反馈」

**这是官方 API 契约**，不是传闻——官方文档写明限制，并提供专门权限去突破它。

「开发者反馈」听起来像「不一定有」，实际是「一定有，且要额外申请」。
**这个差别决定了你要不要在架构里预留分页拉取**。

## 5. 存疑：那张「12 品牌支持情况表」

原始资料里有一张逐品牌的「支持 / 不支持 / 不明确」表。**不要当依据用。**

这类表格是最容易被生成、最难被验证的内容。举一个具体的反例：表里写「Wyze 支持」，
但 Wyze 官方论坛的帖子标题是 *"Android Health Connect Connection - **Wishlist**"*
（[链接](https://forums.wyze.com/t/android-health-connect-connection/285586)）——**那是个功能请求**，
说明至少在那个时间点 Wyze 并不支持。

**建议**：把那张表降级成「待验证清单」，靠第 8 节的实测逐条确认。
真正要覆盖的品牌通常就一两个（你自己手上的秤），没必要为一张不可靠的表做设计。

## 6. 方案对比（修正版）

| 方案 | 需要 `INTERNET` | 实现难度 | 稳定性 | 主要限制 |
|---|---|---|---|---|
| **Health Connect** | **否** ✅ | 低 | 高 | 依赖用户授权 + 品牌 App 愿意写入 + 字段可能不全 + **30 天窗口** |
| BLE 直读 | 否 | 极高 | 中 | 要 bind key、米家抢连接、型号差异大、密钥可能变 |
| 小米云令牌 | **是** ❌ | 低 | 低 | 72 小时过期、风控、2FA、接口非官方 |
| MIoT | **是** ❌ | 高 | 低 | 属性开放不全，大概率只能拿体重 |

**后两个方案的前提就不成立**——不是「难」，是「做了就毁掉卖点」。

## 7. 工程量：拿到数据之后才是大头

原始资料**只谈了「怎么拿到数据」，没谈「拿到之后怎么进库」**。而后者才是本项目里工作量最大的部分。

### 7.1 去重（最大的缺口）

同一次称重可能产生两条记录：

- 用户手动记过一条
- Health Connect 里又读回来一条

两条时间戳相近但不相等，图上就**多一个点**。

Health Connect 每条记录带 `metadata.id`，**必须存下来做去重**。

### 7.2 表结构要动

当前 `WeightRecord` 只有：

```kotlin
id, measuredAt, weightKg, bodyFatPercent, note, createdAt, updatedAt
```

**没有来源字段。** 需要加：

| 新字段 | 用途 |
|---|---|
| `source` | 手动 / Health Connect（将来可能还有 CSV 导入） |
| `externalId` | Health Connect 的记录 id，用于去重 |

**必须写 Room Migration**（约束 2.3）。注意 Migration 要用 `ALTER TABLE ADD COLUMN` 并给默认值，
不能重建表——重建会丢数据。

连带的改动面：

- `RecordValidator`（同步来的记录要不要走校验？它的时间范围/体重范围规则）
- **CSV 导出 / 导入**（导出要不要带 source？导入回来的 source 是什么？`RecordCsvTest` 有 14 个用例）
- `RecordRows` / `RecordRow`
- `Aggregator`（同步数据量可能远大于手动的）

### 7.3 用户删了同步来的记录怎么办

如果用户在 App 里删掉一条同步记录，下次同步它**又回来了**。两种解法：

- 记一张「已忽略的外部 id」表
- 同步来的记录标记成只读，不允许删

**这是个产品决策，不是技术细节**，要单独定。

### 7.4 迁移怎么验（重要）

常规方法**测不出迁移错误**。正确做法：

1. 装 **v1.0 的 release APK**（与新版**同一签名**）
2. 记几条数据，**包括体脂**
3. **直接覆盖安装新版** —— 不要卸载、不要 `pm clear`
4. 确认：数据还在、体脂还在、图表正常、能新增

**第 3 步不能卸载**：卸载重装走的是「全新建表」路径，**根本不会触发 Migration**。
这是 [AGENTS.md 红线 #4](../AGENTS.md)「写入并读回」的跨版本版本。

## 8. 开工前必须实测

> ⚠️ **2026-10 更新**：同步功能**已经实现**（见 [`08`](08-Health Connect 同步设计.md)），
> 但下面这些**依赖真机 + 真秤的实测仍未做** —— 模拟器上能验的（授权流程、可用性判断、
> 读取调用、规划落库、状态渲染）都验了，验不了的是「真实体脂秤到底往 HC 写了什么」。
> 没验到的部分与原因记在 [`04-决策记录` §7.5](04-决策记录.md)。
>
> 顺带：**「30 天读取限制」在模拟器上被 HC 自己的授权页原文复述了一遍** ——
> *"If you give read access, the app can read new data and data from the past 30 days"*。
> §3 里那条官方契约算是又拿到一个独立佐证。

- [ ] 目标体脂秤测量 → 打开品牌 App → 确认数据出现在 Health Connect
- [ ] 确认**具体写入了哪些字段**：体重 / 体脂率 / BMI / 瘦体重（这是最关键的未知项）
- [ ] 确认同步触发条件：是否必须打开 App、是否必须保持蓝牙连接
- [ ] 确认能否读到 30 天前的数据（决定要不要申请 `READ_HEALTH_DATA_HISTORY`）
- [ ] 确认用户拒绝授权时的降级路径
- [ ] 在 API 28 的真机或模拟器上跑一遍（验证 2.2 的版本门槛处理）

**最有价值的线索**：先读 [astrbot_plugin_body_monitor](https://github.com/ludan0312/astrbot_plugin_body_monitor)
的实现，它已经在处理「小米 → Health Connect」这条链路，比从零实测快得多。
但它没明确说体脂率是否写进去了——**那一条仍然要自己验**。

## 9. 未决问题

1. 同步是**只读**（单向拉取）还是要能写回 Health Connect？
2. 自动同步的时机：打开 App 时拉一次 / WorkManager 定期 / 用户手动点？
3. 同步来的记录能不能编辑、能不能删？（见 7.3）
4. 首次接入时要不要**导入历史数据**，还是只从接入那天开始？
5. 冲突时以谁为准：App 内的手动记录，还是 Health Connect 的？
6. 要不要在设置页显示「上次同步时间」和「已同步 N 条」？
