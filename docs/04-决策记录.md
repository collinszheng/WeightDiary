## 1. 由来

原始简报质量很高（视觉描述精确到像素级），但存在若干**歧义或完全未定义**的地方，会直接影响数据模型和界面。这些是全部决策的起点：

| # | 简报里的缺口 |
|---|---|
| ① | 「概览卡片 1 是选中状态」——但没说卡片能否点击，也没说「选中」意味着什么 |
| ② | 「水平」四色条的四段宽度没有定义，而 BMI 无上界 |
| ③ | BMI 分级用中国标准还是 WHO 标准，两套差异很大 |
| ④ | 日 / 周 / 月 / 年 / 总 各自怎么聚合，未定义 |
| ⑤ | 同一天是否允许多次记录，未说明 |
| ⑥ | 身高是档案字段还是每次记录的一部分 |
| ⑦ | 「小的目标线标识」语义不明 |
| ⑧ | 图表的「左右滑动」是切范围还是滚动视口，且简报同一句话里两种说法并存 |
| ⑨ | 「总」tab 时日期范围选择器显示什么 |
| ⑩ | **空状态完全没定义**，而那是用户看到的第一屏 |
| ⑪ | 数据归属与隐私（本地还是云） |
| ⑫ | **App 名称从头到尾没有出现** |

| **A6** | 目标卡片底部细线 | **进度条**：起点 = 设置目标时的体重，终点 = 目标体重 | 纯装饰性刻度 | 装饰性元素在极简设计里不该占位；进度条能提供真实信息 |
| **A7** | 折线空缺处理 | **跨过空缺直接连线**（后由 B17 细化为连续平滑实线） | 断开不连线 | 断点多了线条会碎，破坏曲线观感 |

### 2.2 Q 档 · 产品形态（第一轮）

| # | 决策点 | 结论 | 曾考虑的替代 | 否掉的原因 |
|---|---|---|---|---|
| **Q1** | BMI 分级标准 | **中国标准**：<18.5 / 18.5–23.9 / 24.0–27.9 / ≥28.0 | WHO 标准（25.0 / 30.0 分界）；或做成可配置 | 简报用词「肥胖前期」正是中国标准的术语；同一体重在两套标准下可能一个显示「标准」一个显示「超重」。做成可配置会多一层设置项，v1 不必要（数据模型仍保留 `bmiStandard` 字段以备扩展） |
| **Q2** | 概览卡片可点击 | ~~可切换图表指标（体重 / BMI / 体脂率）~~ **→ 已由 D1 推翻**：卡片整组删除 | 不可点击，选中态仅作视觉强调 | 当时认为「若不可点击，『选中』就失去含义」。**这个理由本身没错，错的是前提** —— 后来发现切换指标这个动作本身没必要，见 D1 |
| **Q3** | 图表实现 | **自绘 Canvas** | Vico / YCharts / MPAndroidChart | 本设计规格极具体（恰好 4 档整数刻度、5 个 X 标签、空心圆点、渐变填充、带标签的虚线目标线），用图表库要一路对抗其默认行为；且「四色条 + 三角滑块」无论如何都得自绘 |
| **Q4** | 数据存储 | **纯本地** Room + DataStore | 本地 + 云同步（需账号体系） | 健康数据敏感，纯本地隐私成本最低、开发最快。代价是换机即丢，因此 P1 的导出 / 备份是这块取舍的**兜底，不是可选项** |
| **Q5** | 身高字段归属 | **档案字段**（`UserProfile.heightCm`） | 每次记录附带身高快照 | 身高低频变更，做快照会让数据模型和写入逻辑都变复杂。代价：改身高后历史 BMI 会全部重算（这通常是期望行为） |
| **Q6** | 同一天多条记录 | **允许**，记录带时间戳 | 一天只保留一条（后写覆盖） | 早晚各称一次是常见习惯；数据模型一开始就带时分，后期改动成本很高 |
| **Q11** | 项目起点 | **新建正式项目** | 复用环境验证时的 HelloApp 脚手架 | HelloApp 的包名是 `com.example.helloapp`，且带着验证期的残留代码，不如干净新建 |

### 2.3 B 档 · 体验细节（第二轮）

| # | 决策点 | 结论 | 曾考虑的替代 | 否掉的原因 |
|---|---|---|---|---|
| **B1** | 变化量显示 | 历史列表 + 概览卡片都显示 | 不显示；或只在列表显示 | 简报完全没提，但「降了还是涨了」是体重 App 的高频期待，不显示就得用户自己心算 |
| **B2** | 编辑 / 删除记录 | **本期做** | 延后到 P1 | 数据录入必然会有错，没有编辑/删除等于录错就无法挽回 |
| **B3** | 数据点点击详情 | 做轻量版点击气泡（日期 + 数值 + 变化量） | 不做 | 比去列表里翻找方便得多，实现成本也就是一次命中测试 |
| **B4** | 数据点抽稀 | 超过 **120 个点**自动按月聚合 | 全量画点 | 点太密会糊成一片，且绘制性能下降 |
| **B5** | 「上滑加载更多」 | **本地全量加载**，按钮只作为打开全量列表的入口 | 真分页（Paging 3） | 数据在本地 Room，几千条一次性加载毫无压力。**真分页属于过度设计** |
| **B6** | 日期范围选择器 | **可点击弹日期选择器** | 只能点左右箭头 | 想跳到半年前的数据要点几十次箭头 |
| **B7** | 备注字段 | **加，选填** | 不加 | 成本极低（一个可空列），但以后想用就要做数据库迁移 |
| **B8** | 目标线撑开 Y 轴 | 是，但**限制幅度**：差值超过区间 30% 时改为只显示方向箭头 | 无条件撑开；或完全不撑开 | 无条件撑开会让折线被压成一条平线，完全看不出趋势；完全不撑开则目标虚线画不出来 |
| **B9** | 目标达成反馈 | 目标卡片变绿 + 一次性微动效 | 弹窗庆祝；或不作反馈 | 弹窗会打断操作；完全不作反馈则用户感受不到达成 |
| **B10** | 输入校验 | **超出范围直接拒绝**（保存按钮禁用 + 提示） | 给警告但仍允许保存 | 直接拒绝能挡住手滑（把 68.5 输成 685）。代价是真实极端值（严重肥胖期）录不进去，属已知取舍 |

| **B13** | 四色条比例 | **四段等宽（各 25%）** | 按 BMI 数值跨度等比 | 等比更「物理准确」，但四段视觉宽窄差异很大（绿段 5.5 vs 深红段 12）。选整齐，代价是滑块必须改为**段索引 + 段内比例**映射（见 [技术设计 §4.2](03-技术设计.md)） |

| **B15** | 周 / 月聚合取值 | **当日最低值**；年取月平均 | 当日最后一条；当日平均 | 当日最低值通常就是晨起空腹体重，是体重管理里最有参考价值的读数；平均值会把早晚差异拉平 |
| **B16** | 图表刻度密度 | **Y 轴加密**：4 条带数字主刻度不变，补到共 **13 条**水平刻度线。**X 轴相反：刻度线全部不画** | Y 轴只画 4 条主刻度；X 轴画满日历刻度 | 见下方「渲染验证推翻的三个设定」 |
| **B17** | 折线平滑 | **monotone cubic 平滑**；**整条序列连续平滑，空缺处也用实线** | 直线段折线；跨空缺段用虚线 | 见 §3 冲突 3 |
| **B18** | X 轴标签分布 | 标签画在**位置四等分点**上，不吸附数据点；刻度位按日历单位铺满 | 按数据点序号等分；吸附到最近数据点 | 见下方「渲染验证推翻的三个设定」 |

## 3. 冲突收敛记录

有三处**简报内部自相矛盾**或**决策之间打架**，处理过程如下。

### 冲突 1 · 图表滑动的职责

简报原文：「图表支持左右滑动**或**点击左右箭头切换日期范围」——把两个手势当成了同一件事。

但后续选择是「图表内滚动查看数据点」，于是滑动不再负责切范围，职责必须重新划分：

| 手势 | 职责 |
|---|---|
| 点击左 / 右箭头 | **切换日期范围**（唯一入口） |
| 图表内左右滑动 | **滚动视口**查看数据点 |
| 滑到范围边缘 | 停住并回弹，**不自动翻页** |

连带后果：

- X 轴 5 个标签必须**随滚动实时重算**
- 图表横向滚动与页面纵向滚动（`LazyColumn`）、概览卡片横向滚动（`LazyRow`）构成三层嵌套，必须做手势方向判定（风险 R5）
- 已知副作用：视口按点密度计算时，「日 / 周」视图（≤7 个点）**滑动无效果**，见风险 R10，M3 阶段再定夺

### 冲突 2 · 同一天两个数字

简报要求目标卡片显示「用户输入的**最新**体重的数值」，而周 / 月图表取「**当日最低值**」。同一天若称两次就会打架：

| 位置 | 取值 | 早 68.5 / 晚 69.2 时 |
|---|---|---|
| 概览卡片「体重」 | 最新一条 | **69.2** |
| 目标卡片「当前体重」 | 最新一条 | **69.2** |
| 折线图今天这个点 | 当日最低值 | **68.5** |
| 历史记录列表 | 全部原始记录，逐条显示 | 两条都列出 |

**结论：保留差异，用信息标注消除误解。** 体重卡片上增加记录时间标注（如 `今天 20:15`），用户看到 `69.2 今天 20:15` 与图表上的 `68.5` 时，能自己推断出「图表取的是当天最低」。

曾考虑的两个方案：

| 方案 | 否掉的原因 |
|---|---|
| 图表也改用最新值 | 一天称两次时折线会出现早晚锯齿，趋势被噪声淹没 |
| 卡片也改用当日最低值 | 用户刚录入傍晚的 69.2，卡片却纹丝不动，会以为没保存成功 |

### 冲突 3 · 平滑插值 vs 数据诚实性

选择了曲线平滑后，平滑插值会在「没称重」的那几天画出一条看起来非常真实的连续曲线，用户会误以为那几天真的测过。渲染对比确认这确实**会造成误读**（见 [`assets/chart-smooth.png`](assets/chart-smooth.png)）。

曾采用的方案是「分段平滑 + 空缺虚线」——连续区段平滑画实线，跨空缺用虚线，语义清晰。

**最终改为：整条序列连续平滑，空缺处也用实线。**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 分段平滑 + 空缺虚线 | 视觉上诚实，一眼能看出哪段是推测 | 线条断续，破坏曲线的整体观感，图变难看 |
| **整条连续平滑实线** ✅ | 曲线连贯、观感好 | 无法从线条本身区分实测与插值 |

取舍是**视觉优先**，改由**空心圆点**承担「这是真实测量」的语义——它是图上唯一标记在真实记录位置的元素。

副作用（正向）：实现上**不再需要**「按日期连续性切段」的处理，`Aggregator` 输出的点序列直接整体平滑即可，反而更简单。

## 4. 渲染验证推翻的三个设定

这三个问题都是**画出来才发现的**，纸面推演看不出来。记录在此，避免以后再凭想象定视觉参数。

| 设定 | 纸面结论 | 渲染后发现 | 改为 |
|---|---|---|---|
| 次刻度线颜色 `#F7F7F7` | 足够浅，符合极简 | 在纯白背景上**几乎完全不可见**，7 条和 13 条刻度渲染出来没差别，加密等于白做 | `#F2F2F2` |
| X 轴标签按数据点序号四等分 | 逻辑上等价 | 遇到有缺口的月份，标签位置随数据点漂移，间距忽宽忽窄（1日 / 7日 / 17日 / 25日 / 30日），像排版事故 | 按**位置**四等分，不吸附数据点 |
| X 轴画满日历刻度线 | 刻度密＝信息量大 | 月视图 30 条刻度线让图面很碎，与极简调性冲突 | 刻度线**全部不渲染**，只留 5 个日期文字 |

另有一处是写代码时发现的，也已修正：**四段等宽后滑块仍按 BMI 线性映射，导致滑块与色块对不上**，改为「段索引 + 段内比例」。

## 5. 被否方案汇总

想改设计时，先看这里有没有你已经想过的路子：

| 想法 | 为什么不做 |
|---|---|
| 用 Vico / YCharts 等图表库 | 规格太具体，图表库的自动刻度策略要一路 override；四色条滑块反正得自绘 |
| 云同步 / 账号体系 | 与「纯本地、健康数据不出设备」的定位冲突，且工作量翻倍 |
| 一天只存一条记录 | 剥夺了早晚称重的能力，且后期改成多条需要数据迁移 |
| 四色条按 BMI 数值等比 | 视觉宽窄差异过大（绿 5.5 vs 深红 12），整齐度更重要 |
| 跨空缺画虚线 | 试过，线条断续，图变难看 |
| 折线做普通三次样条 | 会**过冲**，在数据点之间甩出根本没发生过的假峰假谷。体重场景必须用保单调的 monotone cubic |
| X 轴画刻度线 | 试过，太碎 |
| 用 Paging 3 做分页 | 本地数据库，几千条一次性加载毫无压力，属于过度设计 |
| 给卡片加 elevation 阴影 | `#FFFFFF` 卡片放在 `#FFFFFF` 背景上，阴影根本看不见 |
| 「我的」设置页 | 超出本期范围，身高与目标体重合并进编辑弹窗即可 |
| 引入 Hilt | AGP 9 + KSP 的版本兼容需先验证；小项目手写 `AppContainer` 足够 |
| 靠 Health Connect 无边界地自动同步 | 会把用户**自己记过**的数据重复导入。要在「漏」和「重」之间二选一，见 §7.1 HC4 |
| 申请 `READ_HEALTH_DATA_HISTORY` 拿全部历史 | 要走 Play 审批，而且时间边界比 30 天更严，拿到了也用不上（§7.1 HC8） |
| 用 WorkManager 定期后台同步 | HC 的后台读取要用户另外去系统里开一个很深的开关；一个体重记录不值得为它引入依赖（§7.1 HC9） |
| 同步来的记录做成只读 | 会造出一行删不掉的记录，与 B2「不能有功能黑洞」冲突。改用墓碑表（§7.1 HC5） |
| 靠 Health Connect 区分家庭成员 | HC 里**没有「人」这个维度**：`dataOrigin` 是写入的 App、`device` 是那台秤。只能做「与你自己历史是否一致」的启发式过滤（§7.1 HC7） |

## 6. BMI 预警进图表（2026-10）

起因是一个需求：**「如果体重在超重或者肥胖的临界值，就可以很清楚地看到临界值在哪里。」**

### 6.1 走错的四条路

都渲染过效果图，都否掉了。记下来免得以后重走：

| 方案 | 为什么不做 |
|---|---|
| **背景色带**（按 BMI 等级给绘图区铺四条底纹） | 只在**有边界落进窗口**时才有信息量。体重在正常区间中部时，日/周/月三个视图会退化成一整块同色，等于白铺 |
| **右侧竖条 / 括号**（画一段表示 BMI 区间 + 等级名） | 数值标签 `BMI 22.2–22.5` 要 110px 右边距 = 卡片宽的 17%；退回只标等级名（「标准」）又和目标卡的四色条完全重复 |
| **把阈值线强制纳入坐标轴** | 窗口宽度永远是 `3 × 主步长`。把 6kg 外的阈值塞进来会让步长从 1 顶到 3，窗口从 3 个单位涨到 9 个，**折线振幅从 47% 掉到 16%** |
| **第二张 BMI 折线** | BMI 与体重**严格成正比**（`BMI = 体重 / 身高²`，身高是常数），同一条曲线换个刻度而已，不增加任何趋势信息 |

### 6.2 最终方案

**阈值线直接叠加在体重图上，只在落进窗口时画。**

```
阈值体重 = BMI 阈值 × 身高²        （沿用设置里的中国 / WHO 标准）
只画落进当前 Y 轴窗口的那些
落不进来的直接不画，绝不为了它撑大坐标轴
```

三条关键取舍：

- **`D1` 删掉三张概览卡片**（体重 / BMI / 体脂率）。BMI 预警已经进图表了，切到 BMI 图这个动作就没有存在意义；BMI 的**数值**本来就在目标卡里显示着。图表从此**只画体重**
- **`D2` 目标线改用「步长判据」**：纳入目标后主步长不变 → 画在轴内；会变大 → 轴按数据走，目标改画绘图区内的角标。产品要求「目标线必须常驻」依然满足，而角标的信息更全（直接写「还差 8.5 kg」）
- **`D3` 体脂率改在目标卡与历史记录行里显示**。体脂测量频率远低于体重，所以：目标卡显示**最近一次填写的**（不是最近一条记录的）；记录行**填了才显示**，加在体重右侧的同一行 —— 只增加行宽，**不让行高参差不齐**

### 6.3 顺带做的收敛

`Metric` 枚举（体重 / BMI / 体脂率）整个删除。切换指标的能力没了之后，它永远只有一个取值。
`Aggregator` 里「当日最低值必须锁定同一条记录」那套逻辑随之消失 —— 那条约束存在的理由是
「不能让体重的点取早上、体脂的点取晚上」，只画体重后自动满足。

**代价**：动了聚合器，13 个用例要改。改完 130 个用例全绿。

### 6.4 踩到的坑

- **角标一开始画在绘图区外面**，正好压在 X 轴刻度那一行上，把「六」挡住了。
  改到**绘图区内部**下沿，那一带因为 `snapCentered` 居中而必然留白
- 目标线和阈值线可能挨得很近（目标刚好设在临界值上），**两个标签会叠在一起**。
  按 y 排序后依次下压解决

### 7.1 决策

| # | 决策点 | 结论 | 曾考虑的替代 | 否掉的原因 |
|---|---|---|---|---|
| **HC1** | 版本 | `versionCode 2` / `versionName 1.1` → **实际发行为 code 3** | 直接跳 2.0 | 是功能增量，与 1.0 同一条主线；迁移验证也按 1.0 → 1.1 走。`versionCode` 定成 3 是因为 1.1-beta 先占用了 2（测试版必须低于正式版，见 [07 §4.1](07-真机测试清单.md)） |
| **HC2** | 去重键 | 新增 `source` + `externalId`（唯一索引） | 只存一个同步水位线，不加列 | 水位线只能做到「不重复**拉取**」，做不到「不重复**入库**」：重叠窗口、点了两次同步、多个品牌 App 各写一条，都会产生重复 |
| **HC3** | 手动 vs 同步的重复 | 邻近认领：**同一本地日 + 体重差 ≤0.1kg** 就挂 id，不新增行 | ±5 分钟时间窗 | **手动记录的时分不可信**（它是「打开表单那一刻」，见 HC12），±5 分钟几乎永不命中。只有日期和体重携带信息 |
| **HC4** | 范围限制 | 时间边界**一刀切**：早于最后一条手动记录的一律丢 | 边界内逐条核对 | 一刀切的代价是「你确实没记过」的历史数据永远进不来，**已知取舍**；换来的是判断逻辑最简 |
| **HC5** | 删除同步记录 | 墓碑表 `ignored_external_ids`，随 v2 迁移一起建 | 同步记录只读不可删 | 会造出一行删不掉的记录，与 B2 冲突 |
| **HC6** | 首次接入 | **先引导用户手动记一条自己的体重**，再接入 | 直接拉 30 天 | 没有那条记录就既没有时间边界、也没有异常过滤的锚点 —— 首次同步会把一家人的数据无差别吞进来 |
| **HC7** | 异常过滤 | 宁可漏不可错：与自身历史差异过大就跳过 + 报数 | 逐条让用户确认 | 一条错记录会毁掉整张趋势图（B15 按当日最低值取值，首页变化量也会被压成 0.0）；漏掉的能手动补 |
| **HC8** | 30 天窗口 | 只拉最近 30 天，不申请 `READ_HEALTH_DATA_HISTORY` | 申请，拿全部历史 | 要走 Play 审批，对体重 App 不划算；而且 HC4 的边界比 30 天更严，这个窗口实际用不上 |
| **HC9** | 同步时机 | 打开 App 前台拉一次 + 设置页手动「立即同步」 | WorkManager 定期 | HC 的后台读取要用户另外去系统里开「在后台访问数据」，路径很深；不值得为此引入依赖 |
| **HC10** | CSV | 表头**不动**（仍是 4 列） | 加第 5 列「来源」 | `externalId` 导出无意义；导入回来只能是 MANUAL，解决不了重复，还要改 14 个用例 |
| **HC11** | 入口 | ~~并入设置页「数据管理」，成为第 4 行~~ → **改为独立「实验功能」一节，并压在默认关闭的总开关下**（推翻理由见 §7.6、§7.7） | 新开一块 / 新页面 | 原判据是「§9 明写三块」。但后来查明**它能不能用取决于第三方 App 是否往 HC 写**（小米官方 App 就不写），混在「数据管理」里会让人以为这是自带能力；再后来发现独立成节仍然常占一行，对用不上的人是噪声 |
| **HC12** | 手动录入的时分 | **认定不需要**：改规格，不做时间选择器 | 补上 `TimePickerDialog` | 用户只需说清「哪一天」，多一级选择多一步操作。这也是 HC3 判据的前提 |
| **HC13** | 对外文案 | 「不联网」精确成「**没有网络权限**」 | 保持原样 | 清单里确实会多出两条 health 权限，表述要和事实一致 |

### 7.2 已知代价
写在这里，免得以后被当成 bug 报：

1. 边界之前、用户**确实没记过**的 HC 数据永远进不来（HC4）
2. **首次同步必然 0 条** —— 引导记录的时间就是边界（HC6 + HC4）。这是**有意的**，
   但文案必须说清「从现在开始记录新的称重」，不能只报「0 条」，否则用户以为坏了
3. 两个人体重接近时无法区分（HC 里没有「人」这个维度）
4. 同步先进库、用户**后**手动记了同一次称重 → 两条并存
5. CSV 导出丢失 `externalId`
6. 方案 B（邻近认领）实际覆盖面很窄：一刀切之下边界是所有手动记录时间的最大值，
   任何晚于它的记录都在全部手动记录之后，所以「同日同重」只可能发生在边界当天的更晚时刻。
   保留它是因为成本极低（一个纯函数 + 几个单测），且将来若把边界改回「逐条核对」它立刻变成主力
7. 多成员档案本期不做，见 §8

### 7.3 顺带发现的 bug

`AddRecordForm` 的时间选择器是**死代码**：`showTimePicker` 全仓没有一处设为 `true`，
`TimePickerDialog` 分支（`AddRecordForm.kt:299`）永不执行。而规格（`02-设计规范` §5.1）
当初写的是「日期 + 时间选择器」—— 只有日期被接上了。

**处置：认定不是实现漏了，是规格写多了**（HC12），规格已修订。死代码本次不删，
登记在 `08` §10 的待办里。

这也是 HC3 那条判据成立的前提：**别在别处按「手动记录的时间可信」写逻辑。**

### 7.4 权限说明 Activity：先判断错、再被实跑打脸（值得记一笔）

**最初的判断是错的。** 起初认为 `ACTION_SHOW_PERMISSIONS_RATIONALE` 那套清单声明
只是**上架合规**用的 —— 它们的字面量在 `connect-client` 的 AAR 里找不到
（不是库常量，是 Google 的清单约定），而官方文档站抓不到正文，逐字核实不了，
于是先不写，并在文档里断言「不影响同步功能本身」。

**在模拟器上实跑才发现它是功能性的**：HC 的授权页在弹出来之前会先解析这个 intent，
解析不到就直接 `finish()`，自己的日志只留一句

```
E PermissionsActivity: App should support rationale intent, finishing!
```

用户看到的现象是**「点了「体脂秤同步」那一行，什么也没发生」**。
也就是说：缺了它，这个 feature 在 Android 14+ 上**根本拿不到权限**。

**修好了，而且这次不是靠记忆**，四个字面量全部从实机提取核实：

| 常量 | 出处 |
|---|---|
| `androidx.health.ACTION_SHOW_PERMISSIONS_RATIONALE` | HC 控制器的 dex（就是抛这句错的那段代码） |
| `android.intent.action.VIEW_PERMISSION_USAGE` | HC dex + 平台 `android.jar`（`Intent.ACTION_VIEW_PERMISSION_USAGE`） |
| `android.intent.category.HEALTH_PERMISSIONS` | HC dex |
| `android.permission.START_VIEW_PERMISSION_USAGE` | 平台 `android.jar`（`Manifest.permission`） |

**教训**：`connect-client` 的 AAR 装不下平台约定，所以「库里找不到」不等于「不需要」。
判断不了的时候，**去实跑一次比去猜一次便宜**。

### 7.5 本次没验到的

- **HC 里真有称重记录 → 导入进库**这条路径**没有在设备上跑过**。
  模拟器（API 37）的 HC 里是空的，而 `cmd healthconnect` 只能插**步数**记录，
  没有可用的注入口。所以「真实记录的字段映射（时间 / 公斤 / 体脂百分比 / metadata.id）」
  只由编译期与 AAR 的 API 形状保证，**没有数据级验证**。
  已经验到的是：可用性判断、授权弹窗、读取调用、规划、落库、水位线、状态渲染。
  要补这一环，需要真机上的真秤（`docs/06` §8 那 6 项本就是同一件事）。
- `docs/06` §8 的 6 项开工前实测一条都没做（需要有秤 + 真机）。

> **上面第 1 条已在 2026-10-08 补上**：写了个一次性 seeder App 往真机 HC 里灌了体重 + 体脂，
> 「HC 有真实记录 → 导入进库」跑通了 —— 含体脂配对、离群过滤、邻近认领、去重、墓碑。
> 结果见 [`09-真机实测记录.md` §6.13 与 §6.18](09-真机实测记录.md)。
> 而且过程中**抓到并修掉了一个真 bug**（体脂率配到了错的那一行，§6.15）——
> 恰恰就是「没有数据级验证」这件事本身埋着的雷。

### 7.6 体脂秤同步的入口改成独立「实验功能」一节（推翻 HC11）

**为什么推翻**：HC11 当时判它「同步本质是数据进出，和导入导出同组最自然」，
前提是**它一定能用**。后来查明这个前提不成立 —— **能不能用取决于第三方 App
愿不愿意往 Health Connect 写**，不是本 App 能控制的事；小米官方那个 App 就不写（实测）。

于是继续放在「数据管理」里会给出**错误的暗示**：用户会以为这是自带能力，
用不了时只会觉得是坏的，而不是「数据源根本没写进来」。

**现在的做法**：独立成「实验功能」一节，行下常驻一句说明
（`settings_hc_experiment_hint`）—— 行为可能随版本变化；数据来自「健康数据共享」，
需要体脂秤 App 自己把称重写进去；不是所有品牌的 App 都会写。

HC11 的另一半**没变**：**API < 28 时整节不出现**（连标题一起）——
宁可功能不出现，也不能留一张空卡片配一句「此功能不支持」（`06` §2.2）。

### 7.7 实验功能加总开关，手动/自动同步分开（2026-10）

**为什么还要加总开关**：§7.6 解决的是「别让人以为这是自带能力」，但独立成节仍然
在设置页常年占着一行 —— 而对**绝大多数用户**（体脂秤 App 不往 HC 写）这行永远是「用不了」。
默认关闭、由用户自己打开，才是诚实的默认值：**没开过开关的人，不该在设置里看到自己用不上的功能。**

**为什么手动、自动分成两个开关，而不是一个三选一**：这是两个正交的需求 ——
「我要自己控制什么时候同步」和「我不想管，开机顺手拉一次」。合成一个单选钮，
「既想手动点、又希望启动兜一次」这种组合就无法表达了。

**四条约定**（问过用户后定的）：

| 问题 | 定下来的做法 |
|---|---|
| 两个同步开关能否同时开 | **能**，互不影响 |
| 两个都关着时，那行还能点吗 | **能**，但只用于授权与看状态，**不发起同步** |
| 自动同步时没授权 / 没锚点 | **静默跳过**，不弹窗不打断启动 |
| 打开总开关时，手动同步默认开吗 | **不开**，默认关闭 |

**「生效」判定落在** `ExperimentalUi.manualActive = enabled && manualSync`、
`autoActive = enabled && autoSync` —— 不能只看子开关，否则总开关关掉后首页按钮还在
（子开关的值是要保留的，见下）。

**自动同步放 ViewModel 的 `init`，不放 Activity 的 `LaunchedEffect`**：
`init` 的生命周期是**进程**，旋转屏幕不会重放；自动同步的语义正是「每次启动一次」。

**一个踩过的坑**：`init` 里**不能靠 `uiState` 判断授权** —— DataStore 读开关与系统查询
授权都是异步的，`uiState` 首帧的 `granted` 还是默认 `false`，据此判断会让自动同步
**永远不发生**（不报错，只是静默不干活）。改成先 `await refreshSyncStatus()` 跑完，
再读 `syncAvailability.value` / `syncGranted.value`。

**总开关关掉时保留什么**：已同步的记录保留、两个子开关的值保留（再打开还是原配置）、
入口隐藏。「清空所有数据」只删同步水位线、**不动开关** —— 清数据不是恢复出厂。

**验证方式**：模拟器上确认「关着时那一节只有总开关、打开后四行齐、开手动后首页出现按钮」；
自动同步用**水位线**取证 —— 只留自动同步 → 强杀进程 → 冷启动 → 设置页「上次 …」
从 `09:39` 变成 `09:41`（全程没有任何点按）。

### 7.8 同步的反馈：按钮转圈 + 最短可见时长 + 首次文案分离（2026-10）

**用户的原话**：「给同步按键加一个点击转圈的动画，返回的文案现在是『已连接，将从现在开始
记录新的称重』，感觉表达的有问题。」两件事，根因不一样。

**① 转圈**：`SyncIconButton` 有了 `syncing` 参数后一直**只把图标压成禁用色**，
点下去没有任何「在动」的信号。现在同步期间整枚图标旋转（一圈 450ms、线性）并染成强调色 ——
灰图标读起来像「坏了」，而不是「在忙」。

**这是「加载中不用转圈」那条规则的例外，理由要写清**：设计规范 §7 写的是页面加载一律骨架屏；
**这里是刚刚被点的那枚按钮**在做用户主动触发的动作，反馈必须落在那枚按钮上。两者不冲突。

**② 最短可见时长，而且必须是整数圈**：加完转圈后实测发现**根本看不见** —— 模拟器上点一下并连拍 8 帧，
按图标缺口角度逐帧量，8 帧全是空闲态角度（265.5°），说明同步在几十毫秒内就结束了。
于是给 `syncing` 一个最短可见时长：同步跑完若不足一圈，把「正在同步」补足再落下。
否则「点击有反应」只存在于代码里。

**第一版把参数取错了**：一圈 900ms 配最短 450ms —— 结果是**转半圈就被拽回原位**，
看着像抽了一下（用户原话：「应该刚好转一圈然后回到原位，这样才符合直觉」）。
现在把两者**绑成同一个值** `SYNC_SPIN_TURN_MS = 450`（`SyncEntry.kt`），并由
`syncFeedbackMs(spentMs)` 把时长向上补足到**整数圈**：转一圈刚好回到原来的角度，
收尾时与静止态无缝接上，一帧的跳变都没有。慢于一圈的同步，多等的是当前这圈的剩余部分，最多 450ms。

**③ 文案分离**：`snack_sync_start_fresh`（「已连接，将从现在开始记录新的称重」）
原本挂在 `skipped > 0` 上。但**时间边界一旦定下就不再变**，那些早于边界的记录
**每次同步都会被再跳过一次**，所以平常点一下也会看到这句首次接入的话 —— 答非所问。
改由 `SyncFinished.firstSync`（同步**之前**读水位线是否为 `null`）区分：
- 首次：仍是这句（准确 —— 老数据确实不收）
- 之后：统一成「没有新的称重记录」

**之后那句刻意不报条数**（用户反馈：「跳过多少条记录不要了」）：被跳过的那 N 条用户既看不到、
也无从核对，报了只是把提示拉长；而「没有新的称重记录」已经把该知道的都说完了。

**④ 没有另加一条「正在同步，请稍后」（问过用户后定的）**：那句是**进行态**，而同步结果是**完成态**。
本 App 的 Snackbar 会**排队**（`showSnackbar` 挂起直到上一条消失），先进态那条会把结果提示
往后推约 4 秒 —— 用户会看到「请稍后」压着真正的结果。所以进行态交给「按钮转圈（最少 450ms）」
与设置页那行的「正在同步…」表达，不再另弹一条。

**验证方式**：模拟器上点同步并连拍，量图标缺口角度与绿色像素数。第一版（一圈 900ms）抓到 3 帧
「绿色 + 缺口角 272.0° / 239.6° / 52.5°」—— 与**当时**那个 900ms 一圈吻合，但那 3 帧只转到大半圈
就被拽回，正是用户看出来的跳变。改成整数圈后复测（一圈 450ms，连拍 10 帧）：旋转角
12.5° → 200.0° → 320.5° **单调递增**，随后回到 265.5°（= 空闲态角度）且不再是绿色，
即**转满一圈才停、中途没有被拽回**（见 [`09` §6.21](09-真机实测记录.md)）。
同步后界面文案为「没有新的称重记录」。

## 8. 待立项：多成员档案（2026-10）

家庭共用一台体脂秤是真实场景，而 Health Connect **没有「人」这个维度**。
所以同步层只能做「与你自己历史是否一致」的启发式过滤（HC7），
**两个人体重接近时必然失效**（妈妈 55.2 / 女儿 54.8）—— 这是信息量不足，不是阈值没调好。

**真正的解法是 App 内多成员档案**：切换用户，各自的身高 / 目标 / BMI 标准。

它不属于 §5 的「被否方案」—— 是**没考虑过**。本期不做，因为要动 `UserProfile` /
目标体重 / BMI 标准 / 图表 / 设置页，是另一个 feature 的量级。

## 9. 下一步清单（2026-10）

一轮「下一步该加什么」的讨论，逐条确认过。**哪几条动了代码、哪几条只记录**，都在这里。

### 9.1 Android 自动备份：承诺与事实不符（已知问题，代码先不动）

**症状**：App 里两处写着「所有数据仅保存在本机」，但实际上**不成立**。

**证据**：

- `AndroidManifest.xml` 是 `android:allowBackup="true"`
- `res/xml/backup_rules.xml` 与 `res/xml/data_extraction_rules.xml` 都是
  **Android Studio 模板原样** —— 所有 `<include>` / `<exclude>` 都被注释掉了
- 平台的默认行为是：**没有规则就备份全部应用数据**（除 `cache` / `no_backup`）
- 实测（模拟器 API 37：`bmgr enable true` → 切到本地传输后端 → `bmgr backupnow`）：

  ```
  Package com.weightdiary.app with result: Success      备份 140,288 字节
  ```

  而 App 的非缓存数据合计 135,852 字节，其中 `weight_diary.db` + `-shm` + `-wal`
  就占 **135,776（96.8%）**；差额约 3% 是归档头与 512 字节对齐的开销。
  **如果数据库被排除，这个数会掉到 1 KB 上下。**

**关键区分**：App 确实没有 `INTERNET` 权限（有 `tools/verify-no-internet.ps1` 断言），
但**备份是系统做的**，不需要 App 有网络权限。所以「没有网络权限」成立，
**「数据仅保存在本机」不成立**。

**本次处置**（讨论后定的）：

- **代码不动** —— 保留自动备份，把它当换机时的免费兜底
- **文案改成如实表述** —— 见 9.2
- 记为**已知问题**，不是「已知取舍」：取舍是主动选的，这条是**从来没配过**

**将来若要在代码层面处理**（例如只关云、保留设备间迁移），先看清一个不对称：
`data-extraction-rules` 只对 **API 31+** 生效；API 26–30 走 `fullBackupContent`，
那套没有「只关云」这个维度，**关了就是彻底不备份**。这个不对称已确认接受。

> 顺带一个观察：模拟器的 `bmgr list transports` 里有**独立的**
> `com.google.android.gms/.backup.migrate.service.D2dTransport` —— 设备间迁移与云备份
> 是两个独立模式，这也印证了官方文档「某个模式没有规则，那个模式就全备」的说法。

### 9.2 隐私文案改成如实表述

| 位置 | 原文 | 现文 |
|---|---|---|
| 设置 → 关于（`about_privacy`） | 所有数据仅保存在本机 | 数据只在本机处理。若系统开启了备份，备份可能包含本应用数据 |
| 添加数据弹窗底部（`privacy_local_only`） | 所有数据仅保存在本机 | 数据只在本机处理，不会上传 |
| 权限说明页（`rationale_privacy`） | …不会上传任何内容 | …没有网络权限；若系统开启了备份，备份可能包含本应用数据 |

### 9.3 换机兜底：设置页加一句常驻提醒

数据只在设备上，导出是唯一的兜底，而用户只会在**丢了之后**才意识到。
所以「数据管理」组下面常驻一句（`settings_data_hint`）：

> 数据只在这台设备上，换手机或卸载重装都拿不回来 —— 建议定期导出备份

### 9.4 列表标出记录来源

家庭共用一台体脂秤时，用户要判断「这条是不是我的」，而**这是唯一的线索**
（HC 里没有「人」这个维度，见 §8）。

- `RecordRow` 带上 `source`，`RecordRows.build` 透传
- 列表右侧：`今天 12:45` → `今天 12:45 · 体脂秤`（只在同步来的行上出现）
- 读屏单独念一句「来自体脂秤」—— 可见的是短符号，朗读要念全

### 9.5 Room 迁移改成自动化验证

以前只能手工覆盖安装（`06` §7.4）。新增
`app/src/androidTest/.../WeightDatabaseMigrationTest.kt`，`./gradlew connectedDebugAndroidTest` 跑。
做法与「为什么不用 room-testing」见 [`08` §9.6](08-Health%20Connect%20同步设计.md)。

**顺带明确一个事实**：手工覆盖安装验不出「哪些数据丢了」，只能验出「应用崩没崩」。
红线 #5 的风险比之前认为的高。

### 9.6 等真机再定的两条

- **被跳过的记录能不能回看** —— 现在只报「跳过 N 条」。当时为了界面简洁选了只报数，
  但那是在没上真机之前定的；看到真机上实际跳过什么之后再定更准
- **日视图的 X 轴位置** —— 同一天两次称重的时间戳都是「打开 App 那一刻」，日视图的位置
  会失真（周/月取当日最低值，不受影响）。先看真机上有多明显，再决定要不要让用户选时分

### 9.7 明确不做

- **深色模式** —— 已勘察出三个坑（启动白闪、还要一整 `darkColorScheme()`、两个语义反转），
  纯投入、不修任何风险。继续搁置
- **多成员档案** —— 见 §8。是那个场景唯一的真解法，但体量是另一个 feature
