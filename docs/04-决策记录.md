## 1. 由来

原始简报质量很高（视觉描述精确到像素级），但存在若干**歧义或完全未定义**的地方，会直接影响数据模型和界面。这些是全部决策的起点：

| # | 简报里的缺口 |
|---|---|
| ① | 「概览卡片 1 是选中状态」——但没说卡片能否点击，也没说「选中」意味着什么 |
| ② | 「水平」四色条的四段宽度没有定义，而 BMI 无上界 |
| ③ | BMI 分级用中国标准还是 WHO 标准，两套差异很大 |
| ④ | 日 / 周 / 月 / 年 / 总 各自怎么聚合，未定义 |
| ⑤ | 同一天是否允许多次记录，未说明 |
| ⑥ | 身高是档案字段还是每次记录的一部分 |
| ⑦ | 「小的目标线标识」语义不明 |
| ⑧ | 图表的「左右滑动」是切范围还是滚动视口，且简报同一句话里两种说法并存 |
| ⑨ | 「总」tab 时日期范围选择器显示什么 |
| ⑩ | **空状态完全没定义**，而那是用户看到的第一屏 |
| ⑪ | 数据归属与隐私（本地还是云） |
| ⑫ | **App 名称从头到尾没有出现** |

### 2.2 Q 档 · 产品形态（第一轮）

| # | 决策点 | 结论 | 曾考虑的替代 | 否掉的原因 |
|---|---|---|---|---|
| **Q1** | BMI 分级标准 | **中国标准**：<18.5 / 18.5–23.9 / 24.0–27.9 / ≥28.0 | WHO 标准（25.0 / 30.0 分界）；或做成可配置 | 简报用词「肥胖前期」正是中国标准的术语；同一体重在两套标准下可能一个显示「标准」一个显示「超重」。做成可配置会多一层设置项，v1 不必要（数据模型仍保留 `bmiStandard` 字段以备扩展） |
| **Q2** | 概览卡片可点击 | ~~可切换图表指标（体重 / BMI / 体脂率）~~ **→ 已由 D1 推翻**：卡片整组删除 | 不可点击，选中态仅作视觉强调 | 当时认为「若不可点击，『选中』就失去含义」。**这个理由本身没错，错的是前提** —— 后来发现切换指标这个动作本身没必要，见 D1 |
| **Q3** | 图表实现 | **自绘 Canvas** | Vico / YCharts / MPAndroidChart | 本设计规格极具体（恰好 4 档整数刻度、5 个 X 标签、空心圆点、渐变填充、带标签的虚线目标线），用图表库要一路对抗其默认行为；且「四色条 + 三角滑块」无论如何都得自绘 |
| **Q4** | 数据存储 | **纯本地** Room + DataStore | 本地 + 云同步（需账号体系） | 健康数据敏感，纯本地隐私成本最低、开发最快。代价是换机即丢，因此 P1 的导出 / 备份是这块取舍的**兜底，不是可选项** |
| **Q5** | 身高字段归属 | **档案字段**（`UserProfile.heightCm`） | 每次记录附带身高快照 | 身高低频变更，做快照会让数据模型和写入逻辑都变复杂。代价：改身高后历史 BMI 会全部重算（这通常是期望行为） |
| **Q6** | 同一天多条记录 | **允许**，记录带时间戳 | 一天只保留一条（后写覆盖） | 早晚各称一次是常见习惯；数据模型一开始就带时分，后期改动成本很高 |

### 2.3 B 档 · 体验细节（第二轮）

| # | 决策点 | 结论 | 曾考虑的替代 | 否掉的原因 |
|---|---|---|---|---|

| **B7** | 备注字段 | **加，选填** | 不加 | 成本极低（一个可空列），但以后想用就要做数据库迁移 |

| **B18** | X 轴标签分布 | 标签画在**位置四等分点**上，不吸附数据点；刻度位按日历单位铺满 | 按数据点序号等分；吸附到最近数据点 | 见下方「渲染验证推翻的三个设定」 |

## 3. 冲突收敛记录

有三处**简报内部自相矛盾**或**决策之间打架**，处理过程如下。

### 冲突 1 · 图表滑动的职责

简报原文：「图表支持左右滑动**或**点击左右箭头切换日期范围」——把两个手势当成了同一件事。

但后续选择是「图表内滚动查看数据点」，于是滑动不再负责切范围，职责必须重新划分：

| 手势 | 职责 |
|---|---|
| 点击左 / 右箭头 | **切换日期范围**（唯一入口） |
| 图表内左右滑动 | **滚动视口**查看数据点 |
| 滑到范围边缘 | 停住并回弹，**不自动翻页** |

连带后果：

- X 轴 5 个标签必须**随滚动实时重算**
- 图表横向滚动与页面纵向滚动（`LazyColumn`）、概览卡片横向滚动（`LazyRow`）构成三层嵌套，必须做手势方向判定（风险 R5）
- 已知副作用：视口按点密度计算时，「日 / 周」视图（≤7 个点）**滑动无效果**，见风险 R10，M3 阶段再定夺

### 冲突 2 · 同一天两个数字

简报要求目标卡片显示「用户输入的**最新**体重的数值」，而周 / 月图表取「**当日最低值**」。同一天若称两次就会打架：

| 位置 | 取值 | 早 68.5 / 晚 69.2 时 |
|---|---|---|
| 概览卡片「体重」 | 最新一条 | **69.2** |
| 目标卡片「当前体重」 | 最新一条 | **69.2** |
| 折线图今天这个点 | 当日最低值 | **68.5** |
| 历史记录列表 | 全部原始记录，逐条显示 | 两条都列出 |

**结论：保留差异，用信息标注消除误解。** 体重卡片上增加记录时间标注（如 `今天 20:15`），用户看到 `69.2 今天 20:15` 与图表上的 `68.5` 时，能自己推断出「图表取的是当天最低」。

曾考虑的两个方案：

| 方案 | 否掉的原因 |
|---|---|
| 图表也改用最新值 | 一天称两次时折线会出现早晚锯齿，趋势被噪声淹没 |
| 卡片也改用当日最低值 | 用户刚录入傍晚的 69.2，卡片却纹丝不动，会以为没保存成功 |

### 冲突 3 · 平滑插值 vs 数据诚实性

选择了曲线平滑后，平滑插值会在「没称重」的那几天画出一条看起来非常真实的连续曲线，用户会误以为那几天真的测过。渲染对比确认这确实**会造成误读**（见 [`assets/chart-smooth.png`](assets/chart-smooth.png)）。

曾采用的方案是「分段平滑 + 空缺虚线」——连续区段平滑画实线，跨空缺用虚线，语义清晰。

**最终改为：整条序列连续平滑，空缺处也用实线。**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 分段平滑 + 空缺虚线 | 视觉上诚实，一眼能看出哪段是推测 | 线条断续，破坏曲线的整体观感，图变难看 |
| **整条连续平滑实线** ✅ | 曲线连贯、观感好 | 无法从线条本身区分实测与插值 |

取舍是**视觉优先**，改由**空心圆点**承担「这是真实测量」的语义——它是图上唯一标记在真实记录位置的元素。

副作用（正向）：实现上**不再需要**「按日期连续性切段」的处理，`Aggregator` 输出的点序列直接整体平滑即可，反而更简单。

## 4. 渲染验证推翻的三个设定

这三个问题都是**画出来才发现的**，纸面推演看不出来。记录在此，避免以后再凭想象定视觉参数。

| 设定 | 纸面结论 | 渲染后发现 | 改为 |
|---|---|---|---|
| 次刻度线颜色 `#F7F7F7` | 足够浅，符合极简 | 在纯白背景上**几乎完全不可见**，7 条和 13 条刻度渲染出来没差别，加密等于白做 | `#F2F2F2` |
| X 轴标签按数据点序号四等分 | 逻辑上等价 | 遇到有缺口的月份，标签位置随数据点漂移，间距忽宽忽窄（1日 / 7日 / 17日 / 25日 / 30日），像排版事故 | 按**位置**四等分，不吸附数据点 |
| X 轴画满日历刻度线 | 刻度密＝信息量大 | 月视图 30 条刻度线让图面很碎，与极简调性冲突 | 刻度线**全部不渲染**，只留 5 个日期文字 |

另有一处是写代码时发现的，也已修正：**四段等宽后滑块仍按 BMI 线性映射，导致滑块与色块对不上**，改为「段索引 + 段内比例」。

## 5. 被否方案汇总

想改设计时，先看这里有没有你已经想过的路子：

| 想法 | 为什么不做 |
|---|---|
| 用 Vico / YCharts 等图表库 | 规格太具体，图表库的自动刻度策略要一路 override；四色条滑块反正得自绘 |
| 云同步 / 账号体系 | 与「纯本地、健康数据不出设备」的定位冲突，且工作量翻倍 |
| 一天只存一条记录 | 剥夺了早晚称重的能力，且后期改成多条需要数据迁移 |
| 四色条按 BMI 数值等比 | 视觉宽窄差异过大（绿 5.5 vs 深红 12），整齐度更重要 |
| 跨空缺画虚线 | 试过，线条断续，图变难看 |
| 折线做普通三次样条 | 会**过冲**，在数据点之间甩出根本没发生过的假峰假谷。体重场景必须用保单调的 monotone cubic |
| X 轴画刻度线 | 试过，太碎 |
| 用 Paging 3 做分页 | 本地数据库，几千条一次性加载毫无压力，属于过度设计 |
| 给卡片加 elevation 阴影 | `#FFFFFF` 卡片放在 `#FFFFFF` 背景上，阴影根本看不见 |
| 「我的」设置页 | 超出本期范围，身高与目标体重合并进编辑弹窗即可 |
| 引入 Hilt | AGP 9 + KSP 的版本兼容需先验证；小项目手写 `AppContainer` 足够 |

## 6. BMI 预警进图表（2026-10）

起因是一个需求：**「如果体重在超重或者肥胖的临界值，就可以很清楚地看到临界值在哪里。」**

### 6.1 走错的四条路

都渲染过效果图，都否掉了。记下来免得以后重走：

| 方案 | 为什么不做 |
|---|---|
| **背景色带**（按 BMI 等级给绘图区铺四条底纹） | 只在**有边界落进窗口**时才有信息量。体重在正常区间中部时，日/周/月三个视图会退化成一整块同色，等于白铺 |
| **右侧竖条 / 括号**（画一段表示 BMI 区间 + 等级名） | 数值标签 `BMI 22.2–22.5` 要 110px 右边距 = 卡片宽的 17%；退回只标等级名（「标准」）又和目标卡的四色条完全重复 |
| **把阈值线强制纳入坐标轴** | 窗口宽度永远是 `3 × 主步长`。把 6kg 外的阈值塞进来会让步长从 1 顶到 3，窗口从 3 个单位涨到 9 个，**折线振幅从 47% 掉到 16%** |
| **第二张 BMI 折线** | BMI 与体重**严格成正比**（`BMI = 体重 / 身高²`，身高是常数），同一条曲线换个刻度而已，不增加任何趋势信息 |

### 6.2 最终方案

**阈值线直接叠加在体重图上，只在落进窗口时画。**

```
阈值体重 = BMI 阈值 × 身高²        （沿用设置里的中国 / WHO 标准）
只画落进当前 Y 轴窗口的那些
落不进来的直接不画，绝不为了它撑大坐标轴
```

三条关键取舍：

- **`D1` 删掉三张概览卡片**（体重 / BMI / 体脂率）。BMI 预警已经进图表了，切到 BMI 图这个动作就没有存在意义；BMI 的**数值**本来就在目标卡里显示着。图表从此**只画体重**
- **`D2` 目标线改用「步长判据」**：纳入目标后主步长不变 → 画在轴内；会变大 → 轴按数据走，目标改画绘图区内的角标。产品要求「目标线必须常驻」依然满足，而角标的信息更全（直接写「还差 8.5 kg」）
- **`D3` 体脂率改在目标卡与历史记录行里显示**。体脂测量频率远低于体重，所以：目标卡显示**最近一次填写的**（不是最近一条记录的）；记录行**填了才显示**，加在体重右侧的同一行 —— 只增加行宽，**不让行高参差不齐**

### 6.3 顺带做的收敛

`Metric` 枚举（体重 / BMI / 体脂率）整个删除。切换指标的能力没了之后，它永远只有一个取值。
`Aggregator` 里「当日最低值必须锁定同一条记录」那套逻辑随之消失 —— 那条约束存在的理由是
「不能让体重的点取早上、体脂的点取晚上」，只画体重后自动满足。

**代价**：动了聚合器，13 个用例要改。改完 130 个用例全绿。

### 6.4 踩到的坑

- **角标一开始画在绘图区外面**，正好压在 X 轴刻度那一行上，把「六」挡住了。
  改到**绘图区内部**下沿，那一带因为 `snapCentered` 居中而必然留白
- 目标线和阈值线可能挨得很近（目标刚好设在临界值上），**两个标签会叠在一起**。
  按 y 排序后依次下压解决
