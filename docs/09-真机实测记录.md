### 6.6 真机抓到的真 bug：目标线被作废的判据挡掉，角标还说反方向

**现象**（小米 11；本周只有一个绘图点 66.0，目标 65.0）：

图上**根本没画目标线**，取而代之的是一个绿色角标 **「目标 65.0 ▲ 还需 1.0 kg」**。
而 `▲` 按 `strings.xml` 的注解是「目标在上方、还需要**增**」—— 可用户当前 66、目标 65，
**实际要减 1.0 kg**。方向和事实反了。

**根因**：`HomeViewModel.buildChart` 里留着一套**早已作废**的判据。

`ChartScaffolder.buildYAxis` 的 KDoc 写着「目标体重**始终纳入范围** —— 产品要求目标线
必须在图上看得见」，单测 `目标线无条件纳入范围 - 哪怕离数据很远` 也守着这一条。
但 ViewModel 还在用决策 B8 时代的 `targetFits`（「纳入目标会不会把主步长顶大」），
**有条件地不把目标交给坐标轴**，于是现场叠出了三个巧合：

| 调用 | 结果 |
|---|---|
| `buildYAxis([66.0])` | 单值退化扩到 65..67 → lo=64.84, hi=67.16 → step 1 覆盖不住（64+3=67 < 67.16）→ **step 2，窗口 [64, 70]** ← 旧代码实际用的就是这个轴 |
| `buildYAxis([66.0], 65.0)` | min=65,max=66 → lo=64.92, hi=66.08 → **step 1，窗口 [64, 67]** |

- 目标 65 **落在旧轴 [64, 70] 之内** → 线本该画得出来，却因 `targetFits=false` 没画
- `below = 65 < 64` 为假 → 判成「目标在上方」→ 输出 `▲ 还需`，**方向反了**

**修法两步**：

1. 目标**无条件**交给 `buildYAxis` —— 回到产品要求与该函数 KDoc 的原意
2. 「画线还是出角标」改由**最终窗口**决定，并把判据抽成 `YAxis.showsReferenceLine()`，
   与 BMI 阈值线**共用同一个** —— 图层注释本来就说这两条线是一组水平参照线，
   从前却各用一套判据

修完角标只在极端跨度连兜底步长都撑不下时才轮到，那时它才真的在报「线在图外」。

**真机验证**（覆盖安装修复版后截图）：

| | 修复前 | 修复后 |
|---|---|---|
| Y 轴 | 64 / 66 / 68 / 70（step 2，窗口 [64,70]） | **67 / 66 / 65 / 64（step 1，窗口 [64,67]）** |
| 目标线 | 不画 | ✅ 绿色虚线 +「目标 65.0」标签 |
| 角标 | ❌「▲ 还需 1.0 kg」（方向反） | 不再出现 |
| 超标线 69.4 | 画了 | 不画（已落在窗口外 —— 正是设计要的「贴近临界值才出现」） |

修复后的轴与 `buildYAxis([66.0], 65.0)` 的预测（step 1、窗口 [64,67]）**逐位吻合**。

> **为什么模拟器没抓到**：模拟器上从没设过目标体重，`target` 恒为 null，
> **这条路径整个没被走到**。真机上有真实目标值才暴露出来 ——
> 这也说明「用真实数据跑一遍」本身就值回票价。

回归测试：`ChartScaffolderTest` 里的
`真机回归 - 目标被旧判据挡掉其实它就在那个窗口里` 与
`showsReferenceLine 只认严格落在窗口内部的线`。

### 6.7 性能实测与「三道墙」

**冷启动**（`am force-stop` 后 `am start -W`，跑 3 次）：

| 次 | TotalTime | WaitTime |
|---|---|---|
| 1 | 237 ms | 241 ms |
| 2 | 237 ms | 243 ms |
| 3 | 219 ms | 225 ms |

稳定在 **220–240 ms**。**无白闪** —— MIUI 的 `PreStartingManager` 取的是我们主题的背景色
（`logcat` 里可见 `Get background color: fff8f8f8 key: com.weightdiary.app_light`），
启动窗口与 App 底色一致。

**内存**：`dumpsys meminfo` 的 TOTAL PSS **68,868 KB ≈ 67 MB**（Compose + Skia 的正常水位）。

**四道墙 —— MIUI 上凡是「自动化操作手机」的路子基本都堵死了**：

| 想做的事 | 手段 | 结果 |
|---|---|---|
| 模拟点击 / 按键 | `input tap` / `keyevent` | ❌ `SecurityException: INJECT_EVENTS` |
| 改系统设置（字体缩放、导航方式） | `settings put` | ❌ `SecurityException: WRITE_SETTINGS` |
| 给 App 授权（**连 debug 包也不行**） | `pm grant` | ❌ `SecurityException: … GRANT_RUNTIME_PERMISSIONS` —— AOSP 里 shell 有这个权限，MIUI 撤了 |
| 切导航栏 | `cmd overlay enable …threebutton` | ⚠️ **命令返回成功、`list` 也显示 `[x]`，但界面毫无变化** —— MIUI 的导航栏归自己的 `force_fsg_nav_bar` 管，不认 AOSP overlay |

**所以 §2.2 的三键导航一条至今没验成。** 要验只有两条路：

1. 人工在手机上调：设置 → 更多设置 → 全面屏 → **经典导航键**
2. 开「USB 调试（安全设置）」，让 `input` 能用

**但 `cmd uimode` 是个例外，它通得过** —— 见 §6.8。所以墙只挡死了
`input`、`settings put`、`pm grant` 这三条命令；凡是有专门 `cmd` 子命令的服务仍有戏
（值得逐个试）。

`pm grant` 被拦有个直接后果：**HC 权限只能人工点弹窗授权**（见 §6.10）。

其余「墙外」能用的手段：`am start` / `screencap` / `uiautomator dump` / `logcat` /
`dumpsys` / `cmd overlay list`（只读）/ `cmd uimode` / `svc power stayon`。

### 6.9 ★ 卡点：HC 里是空的，§2.8 的导入路径测不了

`MANAGE_HEALTH_DATA` 直截了当地回答了这个悬了很久的问题：

```
无数据
具有「健康数据共享」访问权限的应用写入的数据会显示在这里
```

**HC 里一条数据都没有，任何 App 都没写过。** 所以：

- 「真秤写入哪些字段」「体脂率是否进 HC」「共用秤怎么跳过」**全都无从验起**
- 本 App 的同步在 02:32 访问过 HC（`HEALTH_HOME_SETTINGS` 页有记录），
  结果正确地导入了 **0 条**；列表仍是「共 3 条」全手动、无来源标记
  → **「HC 为空时同步不编造、不重复」这条已经验到了**

要往下走只有一条路：**让 HC 里真的有称重数据**。两个办法：

1. **拿真秤称一次**（最真实，还能回答「品牌 App 到底写不写体脂率」）
2. 写个一次性的 seeder App 往 HC 灌数据（能覆盖真秤一次称不出的分支：
   只有体重 / 体重+体脂 / 同一天多条 / 多个来源）

**注意 2 的覆盖度其实更高** —— 一次真实称重只能产生一组字段，
而导入逻辑的分支（体脂配对、邻近认领、去重、墓碑）需要刻意构造的数据才跑得全。

### 6.10 造数据：HC Seeder（一次性测试工具）

§6.9 查明 HC 是空的之后，选了「写 seeder」这条路。做完了，记在这里。

**位置**：`E:\adev\HcSeeder` —— **刻意放在 WeightDiary 仓库之外**：它不是产品代码，
测试夹具不该混进版本库。骨架从 `E:\adev\HelloApp` 复制，省得从零搭 Gradle。
**一次性工具，验完即可删。**

**它写什么** —— 关键设计是**全部用固定的 `clientRecordId`**，
所以重复运行是**覆盖而非新增**，这样「再同步一次应该 0 条新增」这条去重验证才成立：

| id | 时间 | 内容 | 期望 |
|---|---|---|---|
| `seed-a-weight` | T−5min | 68.0 kg | 导入 |
| `seed-b-weight` | T−3min | 67.8 kg | 导入 |
| `seed-b-fat` | T−3min | 20.5 % | **与上一条配对**（核心） |
| `seed-d-weight` | T−2min | 85.0 kg | **离群，应被滤掉** |
| `seed-c-weight` | T−1min | 67.8 kg | 导入（同日、与 b 同重） |

时间都取「当前往前几分钟」，**必须晚于最后一条手动记录**（本次是 02:42）才收得进去。

**怎么跑**：

```bash
cd E:\adev\HcSeeder
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.example.hcseeder/.MainActivity
```

写入 + 读回核对的结果打在 `adb logcat -s HcSeeder` 里。

**两个必须知道的坑**：

1. **它同样需要一个 rationale Activity**，否则 HC 会拒绝弹权限窗、直接 `finishing`
   —— 和 WeightDiary 当初踩的是同一个坑。少了它，弹窗根本不出现。
2. **HC 权限只能人工点弹窗**（`pm grant` 被 MIUI 拦，见 §6.7），
   而且**别在弹窗还开着时用 `am start` 启动别的界面** ——
   会把弹窗挤到后台、看起来像「用户没点」。这一步我踩了一次，白等一轮。

### 6.11 借模拟器补齐 MIUI 堵住的两项

MIUI 拦 `settings put` 与 `cmd overlay`（§6.7 的墙），但**这两项在模拟器上都能用** ——
而且它们本质是**布局健壮性**问题、与具体设备无关，模拟器验的是同一条代码路径。
（例外：「MIUI 安全键盘」那条只有真机能验。）

**§2.3 字体缩放 —— 通过**（模拟器，`settings put system font_scale 1.3`）

1.3 是 MIUI 能调到的最大值，也是这次测的值：

| 检查项 | 结果 |
|---|---|
| 首页卡片不截断 | ✅ 「当前 / 目标体重 (公斤)」「68.5 / 未设置」「BMI --」都完整 |
| 图表 X 轴自动减密、不重叠 | ✅ 一~日七个标签一行排开；Y 轴 70/69/68/67 正常 |
| 设置页三段内容不串行 | ✅ y 区间互不重叠：BMI 标准 221–511 / 数据管理 606–1619 / 关于 1672–1994 |

> 顺带在模拟器上确认 `settings put system font_scale` **能生效** ——
> 反证 MIUI 那条 `WRITE_SETTINGS` 拒绝是**设备特有**的封锁，不是 Android 的限制。

**§2.2 三键导航 —— 通过**（模拟器）

模拟器上 `cmd overlay enable …threebutton` **真生效**：导航栏窗口从手势模式的
`fillx63` 变成 `fillx126`（实测，两次都记下来了），而 MIUI 上同一命令返回成功却毫无变化
—— 又一处对照。

| 检查项 | 结果 |
|---|---|
| 底部按钮栏不遮挡悬浮按钮 | ✅ 悬浮按钮 bounds 底边 2232、导航栏自 2274 起，留 42px；截图确认 |
| 不靠眼睛也能判 | `uiautomator dump` 取 bounds ＋ `dumpsys window` 取导航栏高度，直接比 |

**结论**：三条「必须看得见」的布局项（卡片、图表刻度、设置页分段）在最大字体下都成立；
三键导航下底部内容让位正确。**唯一仍未验的是「MIUI 安全键盘 / 隐私输入模式」那条** ——
它只有真机能测，而真机上需要点击（被拦）。

   早被系统回收了，申请回调不会跑 —— 所以点完「允许」HC 里还是空的。
   再启动一次它就会走 `if (granted.containsAll(...)) seed()` 那条分支，直接写入。
2. **seeder 只申请写权限，所以它自己读不回来**（`SecurityException: ... does not have
   permission to read data ... from other applications`）。这是设计如此 ——
   写入是否成功由 HC 数据管理页来确认，不靠 seeder 自读。

**接下来**：在体重日记里点「体脂秤同步」→ 列表应从「共 3 条」变成「共 6 条」，
新增 3 条带「· 体脂秤」标记、其中一条是 `67.8 kg · 20.5%`，
而 85.0 kg 那条应被离群过滤掉。再点一次应 **0 条新增**（去重）。

### 6.15 真机抓到的第二个真 bug：体脂率挂到了错的那一行

**现象**（小米 11；§6.13 那批 seeder 数据同步之后）：

```
共 5 条
  67.8 kg            今天 02:57 · 体脂秤   ↓0.2
  68.0 kg · 20.5%    今天 02:55 · 体脂秤   ↑1.0   ← 体脂挂在这条上
  67.0 kg            今天 02:42（手动）
```

而 seeder 写进 HC 的是 **体重 67.8 @ 02:57 ＋ 体脂 20.5% @ 02:57**（**同一时刻**，
这正是体脂秤的常态）。设计文档 §4.1 第 2 层写得很清楚：体脂按「同一本地日 +
**时间最近**」配对。02:57 的体脂离 67.8（同刻，0 分钟）明明比离 68.0（02:55，2 分钟）更近
—— **配错了**。

**根因**（`MeasurementPairing.pair`）旧实现是：

```kotlin
weights.sortedBy { it.measuredAt }.map { weight ->
    val nearest = candidates.minByOrNull { abs(它到 weight 的时间差) }
    …
}
```

**按体重的时间升序、各自抢「离自己最近的」** —— 这是**先到先得**，不是「时间最近」。
先被处理的 68.0 先把体脂抢走，轮到 67.8 时队列已空。

**真实世界很容易撞上**：一天称两次（早晚各一次）、秤把体脂写在晚上那次 ——
早上的体重会先把体脂抢走。

**修法**：改成**全局按时间差升序**的贪心 —— 先把同一天所有 (体重, 体脂) 组合按时间差排序，
再依次认领（每条体重、每条体脂最多用一次）。最近的一对先配上，就不会被更远的抢走。

> **顺带修正了一个把错误行为固化的测试。** 原测试 `一条体脂率只能被用一次` 里
> w1(07:45)、w2(07:50)、f1(07:48)：f1 离 w2 更近（2 分钟 vs 3 分钟），但断言写的是归 w1。
> 测试名要守的是「一条体脂只能用一次」（这点没错），可「归谁」是按旧实现的先到先得写死的。
> 已改为断言归 w2，并补了一条真机回归用例。

验证：单测 **166 全绿**（+1）。

### 6.16 顺带确认：同日同重的第二条 HC 记录不插新行（符合设计，但要知道后果）

HC 里还有一条 67.8 @ 02:59，与 02:57 那条同日同重（差 0.0kg ≤ 0.1kg），
所以它被 §4.1 第 3 层的**邻近认领**吃掉了 —— 不插新行，把 `externalId` 写到 02:57 那条上。
列表里确实只有 2 条同步来的记录（02:55、02:57）。**这不是 bug，符合设计。**

**但要记住这个取舍的后果**：用户在 HC 里一天称两次、且**两次体重完全相同**时，
只有一次会进 App。（设计是有意的 —— 手动记录的时分不可信，所以按「日 + 体重」判重。
将来若要支持「同日多次称重」，这条得改。）

**另外**：85.0 kg @ 02:58 没进，符合 §4.4 的异常过滤（|85.0 − 67.8| = 17.2 远超
max(3.0, 5% × 67.8)）✓。被拒的记录**不记墓碑**，所以体重真的变了之后它会自己解禁。

### 6.17 Health Connect 禁止写入未来时间的记录（构造 seeder 时撞上的硬约束）

```
java.lang.IllegalArgumentException: Record time must not be in the future,
  record time: 2026-10-08T05:14:23Z  currentTime: 2026-10-08T05:12:23Z
    at android.health.connect.datatypes.InstantRecord.<init>
    at androidx.health.connect.client.records.WeightRecord.<init>
```

HC 在 `WeightRecord` 的**构造函数**里就拒绝了 —— 不是插入时校验，是**对象构造时就抛**。
所以 seeder 只能写**过去**的时间。

**连锁后果**：WeightDiary 的边界是「丢弃 `measuredAt ≤ T`，T = 最后一条手动记录」
（§4.3），而手动记录的时间戳**永远是「此刻」**（`AddRecordForm` 的时间默认取打开表单
那一刻，时间选择器是死代码 —— 见 [08 §4.2](08-Health%20Connect%20同步设计.md)）。
**两条约束一夹，seeder 造的数据就只能靠「等」**：等够 5 分钟，它写出的 `now−5min`
才晚于那条手动记录。

> **测试工具自身的教训**：我原先把 `listOf<Record>(…)` 放在 `try` 外面，于是这个异常
> 直接崩了工具、既没打「写入成功」也没打「写入失败」，害我先怀疑是 HC 没授权或写入
> 静默失败。**构造可能失败的对象的代码，也要放进 `try` 里。**

> **另一条值得记的**：WeightDiary 自己 §4.5 那条「`measuredAt > now + 10 分钟` → 丢弃」
> 对 HC 写出的记录**永远不会触发**（HC 根本不允许未来时间）。它是**防御性**的，
> 针对的是设备时钟在写入与读取之间发生偏移。
> **别因为「测不出来」就以为它没用。**

### 6.20 同步按钮的转圈：**量出来才知道看不见**（模拟器 API 37）

用户反馈「点同步没有任何在动的信号」，于是给 `SyncIconButton` 加了旋转 + 强调色
（设计与理由见 [`04` §7.8](04-决策记录.md)）。**加完先测，才发现问题比想的大。**

**测法**：点一下同步，紧接着连拍屏幕（`build/analyze_gap.py` 沿 360 个角度在半径带
15–22px 采样最暗像素，找最亮扇区当**缺口中心**；同时数图标区域的绿色像素）。

**第一轮（加最短可见时长之前）**：连拍 8 帧，量出来

| 帧 | 缺口中心 | 绿像素 |
|---|---|---|
| tap-1 … tap-8 | **全部 265.5°**（= 空闲态角度） | **全部 0** |

也就是说**一帧都没落在同步窗口里** —— 同步在几十毫秒内就结束了。
（同一批帧里 Snackbar 拍到了：第 2 帧起底部深色占比 0% → 13%。）

**处置**：给 `syncing` 加最短可见时长 `MIN_SYNC_FEEDBACK_MS = 450`。

**第二轮（加完之后）**：

| 帧 | 缺口中心 | 对比度 | 绿像素 |
|---|---|---|---|
| spin-1 | 272.0° | 95 | 494 |
| spin-2 | 239.6° | 86 | 482 |
| spin-3 | 52.5° | 87 | 489 |
| spin-4 … spin-6 | 265.5° | 215–227 | 0 |

前 3 帧**是绿色且在转**（后两帧间隔约 433ms、缺口转过约 173°，与 900ms 一圈吻合），
后 3 帧回到空闲色与空闲角度。**结论：转圈确实发生了，而且只有在补了最短可见时长之后才拍得到。**

同轮验到的文案（同步后读 UI 树）：`没有新的称重记录，跳过 3 条早于启用时间的记录`
（首次同步仍是「已连接，将从现在开始记录新的称重」）。

> **教训**：代码**看起来没问题**不等于用户看得见。「点击有反应」这类反馈要**量持续时间**，
> 否则它会安静地退化成一个只存在于代码里的动画。

> **工具坑（这一节踩过的）**：① 截图必须走 `cmd /c "adb exec-out screencap -p > f.png"`，
> PowerShell 直接重定向会毁掉二进制；② `screenrecord` 是 v1.4，**只支持 mp4、没有
> `--output-format=raw-frames`**，拿不到逐帧，只能靠连拍；③ 顶栏那个齿轮按钮**只有
> `content-desc='设置'`、没有 `text`**，按文字找会漏；④ 页面还在滚动时 `uiautomator dump`
> 的坐标会过期（点不中就是这个原因）；⑤ Compose 的 `Switch` 在 dump 里 `checked` 恒为 `false`，
> 判断开关状态**只能看可见效果**。
