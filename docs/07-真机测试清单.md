# 真机测试清单

> 模拟器上已经验过的项不再重复。这里只列**必须在真机（尤其 MIUI）上复核**的部分。

## 0. 前置：解决 USB 接口被抢

这台机器上装了 **vivo 互传 PC 套件**，它会反复抢占 Android 的 USB 接口，导致 adb 时连时断。

已确认的现象：

- `vivoesService_x64`（普通进程）杀掉后会被 `vivoSyncService`（服务，Auto 启动）拉起来
- 抢占期间 `adb devices` 里设备会间歇性消失，或出现后一条 shell 命令都执行不了
- 手机本身完全正常：接上后设备节点带 ADB 接口签名 `Class_FF&SubClass_42&Prot_01`，WinUSB 驱动绑定正确

**测试前先做其中之一：**

1. 托盘图标右键退出 vivo 互传（最直接）
2. 任务管理器 → 启动应用 → 禁用 vivo 互传的自启
3. 用不到 vivo 手机的话，直接卸载

解法生效后 `adb devices` 应当稳定显示一台 `device` 状态的设备：

```
<序列号>   device   product:...   model:...
```

> 序列号因机而异，每次拔插后 `adb devices -l` 里看到的才是当前的。
> 下文命令里的 `$env:ANDROID_SERIAL` 就是用来指定它的。

## 1. 安装

```powershell
# SDK 位置按自己的来：Android Studio 里 Preferences → SDK Manager 能看到
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"

# 有多台设备时用它指定目标，避免 adb 报 "more than one device"
$env:ANDROID_SERIAL = (Get-Content .\serial.txt -ErrorAction SilentlyContinue)

& $adb install -r ".\dist\WeightDiary-1.1.apk"
```

或者把 APK 拷到手机上直接点安装（需允许「安装未知来源应用」）。

**注意**：release 包与 debug 包签名不同，先卸载旧的再装：

```powershell
& $adb uninstall com.weightdiary.app
```

### 2.0 升级安装：1.0 → 1.1（**最高优先级**）

这是本项目**第一次 Room 迁移**（v1 → v2）。写错就是老用户数据全丢，而
**常规方法测不出迁移错误** —— 必须走真实的升级路径：

- [ ] 先装 `dist/WeightDiary-1.0.apk`（与新版**同一签名**）
- [ ] 记几条数据，**包括体脂** —— 建议故意覆盖三种列：只有体重 / 带体脂 / 带备注

- [ ] 确认：数据还在、**体脂还在**、图表正常、能新增

**第三、四步不能图省事**：卸载重装走的是「全新建表」路径，**根本不会触发 Migration**。
这是 AGENTS 红线 #4「写入并读回」的跨版本版本，详见 [06 §7.4](06-体脂秤接入调研.md)。

**两个只能靠人眼、但比看版本号更直接的确认点**：

- **新二进制确实生效**：添加数据弹窗底部那行 —— v1.0 是「所有数据仅保存在本机」，
  1.1 起是「数据只在本机处理，不会上传」。**看到新文案就说明覆盖安装成功了**
- **迁移确实跑了**：`adb logcat -d` 里搜 `Room` / `Migration didn't properly handle`，
  有任何一条都是失败

> ⚠️ **在 MIUI/HyperOS 上这个测试必须人工操作。** 系统默认拦 `adb shell input`，
> 所以「记几条数据」这步没法自动化（见 §6.2 与 [开发手册 §9.5](开发手册.md)）。
>
> 另外注意 **versionCode 是 1.0 = 1、1.1 = 2**，所以想退回 1.0 必须先卸载
> （Android 只拦降级）—— **而卸载会清数据**。顺序错了就得从头再来。

### 4.1 测试版 vs 正式版怎么出

版本后缀走 Gradle 参数，`appVersionName` 是从它拼出来的，所以**产物名会自动带上后缀**：

```bash
./gradlew distRelease -PversionSuffix=-beta   # → 1.1-beta / WeightDiary-1.1-beta.apk
./gradlew distRelease                         # → 1.1     / WeightDiary-1.1.apk
```

⚠️ **`versionCode` 的排序规则：测试版必须低于它之后的正式版。**
Android 只拦降级（`INSTALL_FAILED_VERSION_DOWNGRADE`），而唯一的绕法是先卸载 ——
**卸载会清掉用户数据**。所以 `1.1-beta` 用 code 2，出**正式 1.1 时要把它改成 3**。

发 Release 时**测试版必须勾 "Set as a pre-release"**：README 首页那个「最新版 APK」
链接指向 `/releases/latest`，而它只认非 prerelease、非 draft —— 不勾会被测试版顶掉。

**密钥库位置**：`keystore/weightdiary-release.jks`，口令在同目录上一级的 `keystore.properties`。

两者都在 `.gitignore` 里。**请务必单独备份** —— 密钥库丢了就没法再发布"同一个 App"的更新，只能换包名重来。

## 5. 命名约定：产物一律用英文名

APK 与导出的 CSV **文件名**都刻意用英文。原因是中文名在 Windows / adb / 手机文件管理器
之间转手时会踩编码坑 —— adb 传的是 UTF-8，PowerShell 按 GBK 解码，文件名会显示成
`浣撻噸鏃ヨ` 这种乱码（实测遇到过）。

- APK：`gradlew distRelease` 产出 `dist/WeightDiary-<版本>.apk`
- CSV：默认文件名 `WeightDiary-YYYY-MM-DD.csv`

**文件内容不受影响** —— 导出的 CSV 表头仍是中文（`时间 / 体重(kg) / 体脂率(%) / 备注`），
因为那份文件是给人用 Excel 看的，不是给机器转手的。

### 6.6 真机抓到的真 bug：目标线被作废的判据挡掉，角标还说反方向

**现象**（小米 11；本周只有一个绘图点 66.0，目标 65.0）：

图上**根本没画目标线**，取而代之的是一个绿色角标 **「目标 65.0 ▲ 还需 1.0 kg」**。
而 `▲` 按 `strings.xml` 的注解是「目标在上方、还需要**增**」—— 可用户当前 66、目标 65，
**实际要减 1.0 kg**。方向和事实反了。

**根因**：`HomeViewModel.buildChart` 里留着一套**早已作废**的判据。

`ChartScaffolder.buildYAxis` 的 KDoc 写着「目标体重**始终纳入范围** —— 产品要求目标线
必须在图上看得见」，单测 `目标线无条件纳入范围 - 哪怕离数据很远` 也守着这一条。
但 ViewModel 还在用决策 B8 时代的 `targetFits`（「纳入目标会不会把主步长顶大」），
**有条件地不把目标交给坐标轴**，于是现场叠出了三个巧合：

| 调用 | 结果 |
|---|---|
| `buildYAxis([66.0])` | 单值退化扩到 65..67 → lo=64.84, hi=67.16 → step 1 覆盖不住（64+3=67 < 67.16）→ **step 2，窗口 [64, 70]** ← 旧代码实际用的就是这个轴 |
| `buildYAxis([66.0], 65.0)` | min=65,max=66 → lo=64.92, hi=66.08 → **step 1，窗口 [64, 67]** |

- 目标 65 **落在旧轴 [64, 70] 之内** → 线本该画得出来，却因 `targetFits=false` 没画
- `below = 65 < 64` 为假 → 判成「目标在上方」→ 输出 `▲ 还需`，**方向反了**

**修法两步**：

1. 目标**无条件**交给 `buildYAxis` —— 回到产品要求与该函数 KDoc 的原意
2. 「画线还是出角标」改由**最终窗口**决定，并把判据抽成 `YAxis.showsReferenceLine()`，
   与 BMI 阈值线**共用同一个** —— 图层注释本来就说这两条线是一组水平参照线，
   从前却各用一套判据

修完角标只在极端跨度连兜底步长都撑不下时才轮到，那时它才真的在报「线在图外」。

**真机验证**（覆盖安装修复版后截图）：

| | 修复前 | 修复后 |
|---|---|---|
| Y 轴 | 64 / 66 / 68 / 70（step 2，窗口 [64,70]） | **67 / 66 / 65 / 64（step 1，窗口 [64,67]）** |
| 目标线 | 不画 | ✅ 绿色虚线 +「目标 65.0」标签 |
| 角标 | ❌「▲ 还需 1.0 kg」（方向反） | 不再出现 |
| 超标线 69.4 | 画了 | 不画（已落在窗口外 —— 正是设计要的「贴近临界值才出现」） |

修复后的轴与 `buildYAxis([66.0], 65.0)` 的预测（step 1、窗口 [64,67]）**逐位吻合**。

> **为什么模拟器没抓到**：模拟器上从没设过目标体重，`target` 恒为 null，
> **这条路径整个没被走到**。真机上有真实目标值才暴露出来 ——
> 这也说明「用真实数据跑一遍」本身就值回票价。

回归测试：`ChartScaffolderTest` 里的
`真机回归 - 目标被旧判据挡掉其实它就在那个窗口里` 与
`showsReferenceLine 只认严格落在窗口内部的线`。

**三道墙 —— MIUI 上凡是「自动化操作手机」的路子基本都堵死了**：

| 想做的事 | 手段 | 结果 |
|---|---|---|
| 模拟点击 / 按键 | `input tap` / `keyevent` | ❌ `SecurityException: INJECT_EVENTS` |
| 改系统设置（字体缩放、导航方式） | `settings put` | ❌ `SecurityException: WRITE_SETTINGS` |
| 切导航栏 | `cmd overlay enable …threebutton` | ⚠️ **命令返回成功、`list` 也显示 `[x]`，但界面毫无变化** —— MIUI 的导航栏归自己的 `force_fsg_nav_bar` 管，不认 AOSP overlay |

1. 人工在手机上调：设置 → 更多设置 → 全面屏 → **经典导航键**
2. 开「USB 调试（安全设置）」，让 `input` 能用

其余「墙外」能用的手段：`am start` / `screencap` / `uiautomator dump` / `logcat` /
`pm grant` / `dumpsys` / `cmd overlay list`（只读）/ `svc power stayon`。
